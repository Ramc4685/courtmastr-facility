The code serves `POST /external-connections/oauth/callback`, a staff route gated by `integrations.connection.manage` that also needs a signed-in person, with a JSON body, and answers `200 {external_connection_id, status, return_url}` (`router.py:159-167`, `schemas.py:176-188`). The yaml still describes the old shape. It also types `realm_id` as `format: uuid`, but the code takes digits only (`schemas.py:179`).
- [contract] Path parameter is `connection_id` in the contract for every `/external-connections/{connection_id}...` operation (openapi-programs.yaml:6780, 6820, 6843, 6884, 6921) and `external_connection_id` in the code (`router.py:170-227`). - [contract] `ExternalConnection` response. The contract returns `granted_scopes`, `settings`, `updated_at` and `authorize_url` "while pending" (openapi-programs.yaml:9197-9220). `ExternalConnectionOut` has none of the first three (`schemas.py:129-139`) and `authorize_url` exists only on the create response (`schemas.py:142-143`, `router.py:156`). - [contract] `createExternalConnection`. The contract documents `409 connection-exists` and `422 provider-not-available` (openapi-programs.yaml:6753). Code: `provider` is a four-value `Literal` of `accounting_file`, `quickbooks_online`, `zoom`, `google_analytics` (`schemas.py:118`), so any other provider (the contract's enum also lists smartwaiver, perkville and more, openapi-programs.yaml:9206) is a generic validation 422 and `accounting_file` and `google_analytics` are in the code but not the contract enum; QuickBooks with the flag off is `422 provider-not-configured` (`service.py:653-656`), not listed; a second `active` or `disconnected` row for the same (provider, location) hits `uq_external_connection` (`models.py:138-140`) and returns the generic `409 already-exists`, while a pending or errored one is now reused instead (see the takeover item below). - [contract] `updateExternalConnection` says settings are "sync_from date, sync mode (invoice or daily summary), auto-sync flag" and the body is `application/merge-patch+json` (openapi-programs.yaml:6811, 9229-9234). - [contract] `runSync` is a job that "creates or retries the accounting_export row of each location and day in the range" and answers an `Accepted` handle `{job_id, status: queued|running|succeeded|failed, resource_url}` (openapi-programs.yaml:6927-6949, 7874-7881). The README says `settings.sync` is "its status and cursor" (lines 151-155), but no route returns it: `ExternalConnectionOut` has no `settings` (`schemas.py:129-139`), `SyncRunOut` is built only inside the POST (`quickbooks.py:354-359`), and the `status_url` it hands back is the exports list (`GET /accounting-exports?external_connection_id=&location_id=`), which shows days posted or failed but not `running`, `failed`-by-dead-letter, the cursor or the counts. - [contract] `SyncMapping` and `SyncMappings`. The contract has an `id` per mapping and a `sync_mapping` table (openapi-programs.yaml:9235-9244). - [contract] The Intuit request id. The contract says "the provider request id is derived from the export id" (openapi-programs.yaml:6931-6932) and ADR 0012 says `"{tenant_id}:qbo_je:{accounting_export.id}"` (adr/0012:180-181, overview 3.12). The README states the new rule (lines 61-63) and the reason; the contract and ADR are not updated. The same id goes to the `accounting_file` adapter's `post_journal`.
- [contract] ADR 0012 section 4 "Schedule" and "Exported days are closed" (adr/0012:183-190). "Sync now" is meant to export the previous day "and any earlier unexported day"; the code exports exactly the requested range, default yesterday, with no catch-up (`quickbooks.py:333`). After a successful export the job is meant to advance `tenant.billing_locked_through_on`; nothing in the module touches it (no match under `backend/app/modules/integrations`), so exported days stay editable. The README says the scheduled sync is not built (lines 166-167) but not the catch-up or the lock; the finished-day rule it adds (lines 63-64) is the nearest the code gets.
- [undocumented] What `local_key` must be. The contract and ADR 0012 say "tax id", "revenue category id" (openapi-programs.yaml:9242, adr/0012:158-166). The export looks mappings up by posting key: `revenue:<category id>`, `tax_payable:<tax id>`, or the bare ledger account name (`domain/journal.py:18-23`, `service.py:818`). A mapping saved with a raw category id never matches. README lines 85-86 mention that posting keys are unique across kinds but not that `local_key` must be one; `unmapped` lists the posting keys (`quickbooks.py:283`), the only hint.
- [undocumented] ADR 0012 refresh rules the README does not list as not built (its lines 166-167 name only `needs_reauth`). A refresh failure (`invalid_grant`) emits no `integrations.connection.failed` and notifies no Owner (`quickbooks.py:94` lets the exception propagate, or `refresh_if_due` swallows it, :105-106; `events.py` has only the webhook-disabled event), and `ExternalConnection.failure_count` is never written for connections (`models.py:155`; the only writers are the webhook endpoint, `service.py:317, 557, 567`). The row-lock half of this item is fixed.
- [undocumented] The row lock is wider than the README says. `credentials()` locks the connection row (`SELECT ... FOR UPDATE`) and reloads the ciphertext on every call, not only when a refresh is due (`quickbooks.py:85-87`), so `getSyncMappings` (:274), `revoke` (:202) and each posting hold the lock until the request ends. README lines 154-155 say only that "due tokens are refreshed under a row lock". `refresh_if_due` catches every `Exception` (:105), which includes a database error that would poison the transaction, and it runs only for QuickBooks connections with `quickbooks_enabled` on (`quickbooks.py:372-374`); an `accounting_file` sync never refreshes.
- [undocumented] `getSyncMappings` and every call that needs the access token can refresh and reseal credentials (`quickbooks.py:82-96`, called at :274), so a `GET` writes and now also locks the row. The README rationale for a POST callback ("no mutating GET", lines 70-71) does not mention it. The request transaction commits, so the rotated token is kept.
- [undocumented] `run_sync` rules the README leaves out (its lines 151-155 give the 31-day cap, the location's own dates and `sync-in-progress`): days already `failed` are counted as `failed` and not retried unless `retries_failed` is true (`quickbooks.py:385-386`); today and future days are refused with `422` at the queue time (`last >= today`, :334); a body `location_id` is ignored when the connection has its own (:325); a sync needs an `active` connection (`409`, :321-322); a connection that is disconnected while the job runs ends the job as `failed` with no count for the remaining days (:375-376).
- [undocumented] A `running` sync can stay `running` for good. Only a finished last day (`quickbooks.py:392-393`), the dead-letter hook (`fail_sync`, :400-405; `jobs.py:34-36`) or a disconnect seen by a later chunk clears it, and the guard for a second sync is that flag (:323-324). If the queued message is lost before a chunk runs (the actor sends itself again only after a commit, `backend/app/core/jobs.py:119-121`), there is no cancel route, no timeout and no sweep, so every later sync is `409 sync-in-progress`. The README names the `409` but not how it ends.
- [undocumented] The pending or errored takeover (README lines 163-165) is wider than the text. `create_external_connection` matches on provider and location only, for every provider (`service.py:665-672`), and rewrites the row: `settings` (so mappings, `account_map`, `class_map` and any `sync` cursor are replaced by the request's), the credentials, `external_account_*`, `connected_by_staff_user_id`, `last_error` (`service.py:659-663`, `675-676`). The id and `created_at` stay, and the audit record is still `integrations.connection.create` with no sign that a row was reused. The README does not say that the takeover now kills the earlier starter's link: `_complete` refuses a state whose staff user is not the row's `connected_by_staff_user_id` with `403 state-invalid` "expired" (`quickbooks.py:169-172`), so a different person's earlier link dies. It does not die for the same person: a second start by the same user keeps both sealed states valid for that connection id until one completes the row (the first wins, `status` must still be `pending`). In practice only QuickBooks writes `pending` and `error` (`quickbooks.py:130, 149`), so the other providers never hit the reuse branch.
