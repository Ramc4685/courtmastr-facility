## backend/app/modules/engagement/README.md

- [stale-not-built] Lines 119-120 list "slug routing in the web app (SSP-01)" under Not built, but it exists: `web/src/app/App.tsx:123` mounts `/f/:slug/*`, `web/src/features/entry/FacilityApp.tsx:349` serves the public facility pages, and `web/src/api/client.ts:90` sends the slug as `X-Tenant-Slug`. The README itself says so at line 138.
- [wording] Line 9 says `models.py` holds "15 tables" and lists them. It now has 16: `portal_signup` (`models.py:573`) is missing from the list.
- [undocumented] The file table (lines 7-16) has no row for `signup.py` (`request_signup`, `confirm_signup`; `signup.py:46,69`). It is described only in the Phase 11 section (line 124). Line 11 says `service.py` holds everything else, and `events.py`, `permissions.py` and `schemas.py` are not listed either.
- [contract] The mobile-adapter path at line 112 is wrong. The README names `mobile/src/api/api.ts`, but that file does not exist. The adapter is `mobile/src/adapters/api.ts`; `mobile/src/api/` holds only `client.ts`, `errors.ts`, `schema.d.ts` and `types.ts`.
- [wording] Line 104's heading, "Endpoints the mobile app depends on (keep stable)", overstates what the app uses. The mobile adapter calls only `GET /portal/inbox` (without `client_id`), `POST /portal/inbox/{id}/read` and `POST /portal/devices` (`mobile/src/adapters/api.ts:178,179,181`). No code in `mobile/src` (excluding the generated `schema.d.ts`) calls `/portal/inbox/unread-count`, `DELETE /portal/devices/{id}`, `/portal/videos`, `/public/portal-config` or `/portal/clients/{client_id}/communication-preferences`.
- [wording] Lines 112-114 list the other portal routes the mobile adapter maps, and the list is incomplete. The adapter also calls `/portal/session-listings` (`mobile/src/adapters/api.ts:37`), `/portal/enrollments` and `/portal/enrollments/{id}/cancel` (`api.ts:90,126,133`), `/portal/app-cards` (`api.ts:118`) and `/portal/assessment-bests` (`api.ts:177`).
- [contract] `getPortalVideo` (`GET /portal/videos/{video_id}`) is in the API contract (`docs/api/openapi-programs.yaml:5443-5446`), and `service.get_portal_video` exists (`service.py:1879`). No route serves it: `router.py:442` mounts only `GET /portal/videos`, and nothing calls the service function. The README lists only `GET /portal/videos` (line 109) and does not record the gap under Not built (lines 116-120).
- [undocumented] The context emits three events the README never mentions: `engagement.campaign.sent` (`events.py:9-14`; `service.py:979`), `engagement.message.bounced` (`events.py:17-21`; `service.py:1165`) and `engagement.consent.changed` (`events.py:24-28`; `service.py:1184,1225`). Only `PortalSignupConfirmed` is named (line 128).
- [undocumented] Portal inbox items expire 30 days after they are published. `INBOX_DAYS = 30` (`service.py:352`) sets `expires_at` on announcement and automation items (`service.py:950,1460`), and expired items drop out of the inbox and the unread count (`service.py:1250`). Deviation 4 (lines 73-78) describes inbox read state and recall but not the expiry.
- [undocumented] Two permission keys are registered but used nowhere in code: `engagement.sms_campaign.send` and `engagement.inbox.reply` (`permissions.py:19,23`). The only reference to either is the registration. SMS is listed as not built (line 119). Replying to client messages is not listed as not built, and no route offers it.
- [undocumented] Line 14 says `subject.py` holds the merge and data-subject handlers, but it covers only the four messaging tables (`subject.py:13,46-47`, registered as `engagement_messaging`). A second pair of handlers for `communication_preference` and `consent_event` lives in `service.py`, registered as `"engagement"` (`service.py:286-340`).
- [undocumented] Built-in segments are read-only: an edit or delete gets `409 segment-read-only` (`service.py:688,705`; `BUILTIN_SEGMENTS`/`ensure_builtin_segments` at `service.py:733-748`). The README also omits the system-template catalogue `SYSTEM_TEMPLATES`/`system_template` (`service.py:582-594`) and the `POST /segments/preview` route (`router.py:120`). The Rules section (lines 51-53) refers to "system templates" without saying where they come from.
- [undocumented] Releasing an address that has turned permanent is refused with `409 suppression-permanent`, and releasing one twice gets `409 invalid-state-transition` (`service.py:1124-1127`). Line 56 says only that suppression becomes permanent "after a release".
