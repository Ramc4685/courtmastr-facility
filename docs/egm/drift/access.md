### [undocumented]

- `POST /check-ins/evaluate` (router.py:55-59, a dry-run decision) and `POST /credentials/resolve` (router.py:73-80, `service.resolve_credential`, service.py:355) are not named in the README.
- `GET /clients/{id}/access-mode` (router.py:176-179, key `access.checkin.create`) is not in the README. README 59-60 covers only `PUT`.
- The event `access.check_in.session_booked` (events.py:29-30, published at kiosk.py:129 and desk.py:224) is not listed. README 49 and 147 name `granted`, `denied` and `checked_out`.
- The module consumes `clients.client.disabled` and revokes the client's wallet passes (handlers.py:7-12, `service.revoke_wallet_passes_of`, service.py:592). The wallet-pass section and the merge and erasure bullet (README 157-161) do not mention it.
- Issuing a wallet pass, an app card or a generated credential requires an active client (`clients.service.require_active`, service.py:433, 503, 551). The README does not say so.
- Kiosk name search needs `lookup_method` to allow it, a prefix of at least 3 letters (schemas.py:425-427), lists at most 5 (`NAME_MATCHES`, service.py:58, 808-810) and never lists disabled clients' value lookups (`client.status == "active"`, service.py:801). Lookup refusals are 422 `lookup-method-disabled` (service.py:800, 804, 836). README 73-76 says only that minors are not listed.
- `lookup_method = name` also refuses a scanned member-number barcode at check-in (`card_payload` with no credential row: 422 `lookup-method-disabled`, service.py:835-836) and a typed member number at lookup (service.py:792-800). The README does not say.
- A scan the kiosk cannot match is 422 `card-invalid` and counts toward the lockout (service.py:826-834); the README names neither the code nor that the same count covers lookups and check-ins (README 115-118 says "scanned or typed", which is close, but gives no code). A staff user scanning at the window is not covered by the lockout (`resolve`, service.py:110, is called directly), also unsaid.
- The kiosk cookie lives 400 days (`max_age=400 * 86400`, router.py:402). The README gives no lifetime.
- `kiosk.visit()` spends the visit token with one `DELETE ... RETURNING` (kiosk.py:51-68). README 98-100 states this and `test_a_visit_token_cannot_be_spent_twice_concurrently` (tests/test_kiosk_reservations.py:247) covers it, but the README names no test. The new rules also have tests the README does not cite: `test_a_typed_card_value_is_not_possession` (tests/test_kiosk_reservations.py:273) and `test_repeated_unknown_values_lock_the_kiosk_for_a_while` (:287).
- The household lockout. `clients.households.household_ids` (households.py:353-365) is symmetric: the visitor's lockout comes from a past-due invoice billed to the visitor or to any client one live relationship away whose type grants acting rights in either direction. README 88-90 names only the child billed to a parent; a parent is equally locked through a child's past-due invoice. The only test, `test_a_child_billed_to_a_past_due_parent_cannot_book_at_the_kiosk` (`backend/app/modules/billing/tests/test_collections.py:76`), lives in billing and covers the child case only. Nothing in `access/tests/` covers the household lockout.
- The README's reverted-purchase bullet gives rules for a future version (a fresh app-QR step, no bare wallet passes, one purchase per check-in, a daily cap) but no code, test or contract places mark them. Nothing in the code prevents a later purchase route from skipping them.
- The lockout resets its count to 0 when it trips (service.py:761), so the five-minute window ends with a clean slate, and a value that resolves while a lock is active is still refused (service.py:754-755). README 115-118 says "any value that resolves resets the count", which is true only outside a lock.

### [wording]

- README 76, 90 and 99 use "admitted" for the kiosk status. The stored `check_in.result` is `granted` / `denied` / `granted_override` (models.py:32-35); the kiosk response status is `admitted` / `see_staff` (kiosk.py:145, service.py:852). The README uses both vocabularies without saying which is which. README 13 is right for the stored value.
- README 155 puts "Booking from a check-in marks only the session just booked, and refuses a checked-out visit (409 `already-checked-out`)" inside the Member card (CHK-12) bullet. It belongs with "Book or sell from the window (CHK-04)" (README 138-143; desk.py:199, 224).
- README 105-106 says "Spending anything at the kiosk (a package credit, and in future a membership visit, an account charge or a payment) needs identification by possession". The only spend built is a package credit through `programs.selfservice.kiosk_enroll`; "in future" is accurate but the bullet reads wider than the code.
- README 108-109 says "the tablet sends every scanner burst as `card_payload`". `web/src/features/access/KioskPage.tsx:136` does send a scan as `card_payload` and a picked name match as `match_token` (:209), so the kiosk page agrees. The README does not link that file, so the link between the rule and the screen is only implied; the kiosk lookup route accepts `credential_value` from any device-token client, and the rule rests on the server alone (service.py:839).
