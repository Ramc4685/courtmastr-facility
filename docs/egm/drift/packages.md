## backend/app/modules/packages/README.md

Checked against the uncommitted working tree on 2026-11-13: `postbilled.py`, `service.py`, `models.py`, `schemas.py`, `router.py`, migration `1481`, `backend/openapi.json` and `docs/api/*.yaml`. The post-billed rules this change set added to the README (renewal keeps `billing_mode`, base tier 1, credit-back via `adjust_charge`/`reverse` with `credited_at`, packages of any status with usage, end-of-package rule, per-package savepoint with `failed`) all have code behind them. The items below are what still differs.

Contract (`docs/api/*.yaml`)

- [contract] The whole post-billed surface is still absent from the hand-written contract. The yaml files contain no `post-billed-rates`, `post-billed-closes`, `post-billed-closes/preview` or `client-packages/post-billed` path, and no `billing_mode`, `failed` or `PostBilledCloseFailure` schema (grep of `docs/api/` finds none; the only mention is a note at `docs/api/openapi-money.yaml:82` that BIL-18 paths belong to packages). The router serves them (`router.py:263-301`, `router.py:118`) and the generated `backend/openapi.json` carries them (`/api/v1/post-billed-closes` at line 131589, `.../preview` at 131789, `PostBilledCloseFailure` at 52436). The new `failed` list on the close response therefore exists only in generated output. The README does not say the yaml is behind.
- [contract] `portalQuoteClientPackage` (POST `/portal/client-packages/quote`, `docs/api/openapi-people.yaml` around 5204) is not served. `router.py` has only the staff `/client-packages/quote`. The README "Not built" list names only `setClientPackageRenewal`.
- [contract] `setClientPackageRenewal` (`PUT /client-packages/{package_id}/renewal`) is still a route in the contract (around `openapi-people.yaml:5265`), while the README says it is folded into `updateClientPackage`. The README is right about the code; the contract is stale.
- [contract] The close response is 201 for both a new close and a repeat that returns the first close (`router.py:284`, `postbilled.py:234-235`). `failed` is filled only on a fresh close (`postbilled.py:270`). A repeat, a concurrent-close loser (`postbilled.py:243-246`), `GET /post-billed-closes` and `GET /post-billed-closes/{id}` all return `failed: []` from the schema default (`schemas.py:504`). The README does not say `failed` is not stored and cannot be read back later, so a caller who loses the response cannot see which packages failed except by running a preview.

Post-billed behaviour not (or wrongly) described in the README

- [drift] The close and the preview can disagree about credit-backs. `_plan` builds a line for a package that has only a restored credit and no new usage, with `rate = None` and `skipped_reason = "no-usage"` (`postbilled.py:163-188`). The preview therefore shows it as "no-usage" with total 0, but a real close does act on it, because the close loop skips only lines with neither rate nor credits (`postbilled.py:249-250`, `_credit_back` at `:273-291`). The README says the preview "shows the same lines without writing". The preview line has no field for the pending credit-back (`schemas.py:458-467`).
- [drift] A credit-back writes no line and no total. `_credit_back` adjusts or reverses the original line's charge (`postbilled.py:279-285`) and stamps `credited_at`, but the original `post_billed_line.total_minor`, `session_count` and the old close's `total_minor` are not changed. `PostBilledLineOut` has no field for credited sessions (`schemas.py:477-486`), and the only trace of a credit-back is an audit record `credited_sessions` (`postbilled.py:289`). The README says only that the charge is adjusted.
- [drift] `post_billed_line.charge_id` is rewritten when the charge is adjusted (`billed.charge_id = ...adjust_charge(...).id`, `postbilled.py:283`). When the charge is reversed, `charge_id` and `invoice_id` still point at the reversed charge and its invoice. Neither behaviour is documented. A line whose `charge_id` is null (a tier priced at 0 with no invoice) is credited back with no billing call at all (`postbilled.py:279`); the usage row is still stamped.
- [drift] The failed-package path has an uncovered case. In `close_period`, a failure is caught only as `DomainError` or `IntegrityError` (`postbilled.py:255`). Any other exception aborts the whole close, and the `post_billed_close` row added earlier goes with it, so the README sentence "a failure is listed in `failed`" holds for those two kinds only. The `code` falls back to the literal `conflict` when an exception has no `code` (`postbilled.py:256`). The README does not list the possible `code` values.
- [drift] "billed at a later close" is true only for a later closing date. A close is unique per location and date and a repeat returns the first (`postbilled.py:233-235`), so a failed package cannot be retried by re-running the same date. The README says only "a later close".
- [drift] A package without auto-renew is ended by moving `valid_during` end to `max(lower, closing_on) + 1 day` and then calling `service._expire` (`postbilled.py:326-330`). This expiry window rewrite, the audit and the `PackageExpired` event are not described. The README rule "nothing is held and nothing was used after the closing date" is implemented as "no reserved credits and no unbilled usage of any date" (`postbilled.py:325`, `_usage(..., date.max, ...)`). Only active packages can end (`status == "active"` guard), and a package that has a failed or skipped line (no rate) is never ended at that close.
- [drift] Packages are picked up by `_plan` when they have unbilled usage or a pending credit-back, "whatever their status" (`postbilled.py:163-176`). Packages with no usage at all are listed in the preview only when active. The module docstring says "reported as unsettled" for held credits (`postbilled.py:8`), and `unsettled_count` is the package-wide `sessions_reserved_count`, not only holds on or before `closing_on` (`postbilled.py:182`). The README does not mention the preview field or this scope.
- [wording] The router docstring and `preview_close` docstring still say "Every open post-billed package at the location" (`router.py:282`, `postbilled.py:214`). Since this change they also cover ended or removed packages with usage or a pending credit-back.
- [undocumented] No invoice is created when the charge total is 0 (`postbilled.py:309`), so `post_billed_line.invoice_id` stays null. The README says each package gets "one `create_invoice_for_charges`".
- [undocumented] A usage row is reused when a credited source is used again: one `post_billed_usage` row per source, repointed to the new line with `credited_at` cleared (`postbilled.py:314-321`; unique key `uq_post_billed_usage`). The README mentions "billed again" but not that history of the earlier line is overwritten on the usage row.
- [undocumented] `credited_at` is a model and migration column (`models.py:581`, migration `1481:230`) but is not in any response schema or in `docs/architecture/data-model-people.md`. That document still says PKG-11 has "no columns reserved" (around lines 1097 and 1719), so none of the four `post_billed_*` tables are in the schema of record.
- [undocumented] Rates. `GET/POST /post-billed-rates` and `PATCH /post-billed-rates/{id}` (`router.py:263-277`, gate `packages.plan.manage`, `postbilled.py:51-88`) are not described. The base-tier check runs on create and update only for active tiers and only when some tier exists (`postbilled.py:81-88`), so a reservation type with no tiers is allowed until the first one is added, and that first one must be `min_sessions = 1`. Rate uniqueness (`uq_post_billed_rate_tier`, code `rate-tier-exists`, `postbilled.py:41`) is not in the README. Rates that existed before this change with no tier 1 are not migrated or flagged, so `_tier` can return no rate for a small count (`skipped_reason = "no-rate"` remains reachable, contrary to the README claim "every used session has a rate").
- [undocumented] `open_package` details: sale gate is `packages.package.sell` at the location, not a post-billed key; `share_with_related`, `is_autopay` and `is_auto_renew` inputs; default name "Post-billed sessions"; `invoice_mode = none`; sales channel `staff` (`postbilled.py:101-128`).
- [undocumented] Renewal of a post-billed package ignores `renews_as_plan_id` and a source contract plan (`service.py:923-924`), so a post-billed package can never switch to a plan. The README says only "A renewal stays post-billed". The copy list now includes `billing_mode` (`service.py:943`).
