### New since the last report (calendar feeds, public schedule)

- [contract] `listCalendarFeeds` declares `x-permission: integrations.calendar_feed.revoke_any` (`docs/api/openapi-programs.yaml:7063`). The route is a bare `require()` (`router.py:203`): any staff user lists their own feeds, and `revoke_any` only widens the list to others' feeds in their locations (`feeds.py:63-72`, `_visible`). The README (lines 66-68) matches the code, so the contract is the one that differs.
- [contract] `updateCalendarFeed` is summarised as "Change filters, or disable and re-enable" (openapi-programs.yaml:7078). `CalendarFeedUpdate` accepts only `name`, `include_shifts` and `status` (`schemas.py:192`). Location and team cannot be changed, so there is no filter to change.
- [contract] The nine operations in the task carry only a summary and permission, with no parameters, request bodies or response schemas: the five staff and portal feed operations (`openapi-programs.yaml:7057-7099`), `getPublicCalendarFeed` (:7100) and the three public-schedule ones (`openapi-core.yaml:3354-3380`). The code requires `location_id` on `GET /public/schedule` and `GET /public-schedule-settings`, and takes `from_on` and `days` (1 to 31) on the first (`router.py:263, 280-287`). The contract's `getPublicSchedule` declares no parameters at all (openapi-core.yaml:3354-3362).
- [contract] The three public-schedule operations are tagged `[scheduling]` in the contract, but the generated spec tags them `['integrations', 'scheduling']` (`backend/openapi.json`, `/api/v1/public/schedule` and `/api/v1/public-schedule-settings`). The router-level `tags=["integrations"]` (`router.py:25`) is added to the per-route `tags=["scheduling"]` (:262, 268, 277).
- [contract] The `getPublicCalendarFeed` description says the token is "revocable and rotatable from the portal" (openapi-programs.yaml:7106-7108). A member can only create a feed: `POST /portal/calendar-feeds` (`router.py:232`) is the only portal route. Disable, re-enable and delete go through `_manage`, which calls `_staff_only` (`feeds.py:137-138`), so a member cannot list, revoke or rotate their own feed. Repeated POSTs also mint unlimited member feeds (`feeds.py:123-134`, no uniqueness check). Neither the README nor the contract lists a portal revoke route.
- [stale-not-built] The status docs still say calendar feeds and the public schedule are not built. `docs/status/16-integrations.md:23` says of INT-08 "Only the `integrations.calendar_feed.revoke_any` permission is registered". `docs/status/02-resources-scheduling.md:46-47` and `02-resources-scheduling-web.md:46-47` say the same of SCH-19 and SCH-20, `docs/status/12-staff.md:29` of STF-13, and `docs/status/README.md:97-98` of SCH-19 and SCH-20. `backend/app/modules/scheduling/README.md:105-106` lists "public schedule (SCH-20)" and "calendar feeds (SCH-19)" under "Not built", and does not mention that integrations now serves them (`feeds.py`). I did not find a status row for LGE-25 or SSP-19 in the files I searched.
- [undocumented] The README never names the key `scheduling.public_schedule.manage`, which gates `/public-schedule-settings` (`feeds.py:35`, `router.py:263, 270`; registered at `backend/app/modules/scheduling/permissions.py:42`). The settings write audits as `scheduling.public_schedule.update`, a scheduling-namespace action written by integrations (`feeds.py:321`, `update_public_schedule_settings`). A GET for a location with no row returns unsaved defaults (off, 7 days, sessions on, busy off), not a 404 (`feeds.py:312`).
- [undocumented] Public schedule delivery details are missing from the README. `GET /public/schedule` is rate limited as `public-schedule`, 60 a minute per IP (`config/app.yaml:77`). It sends `Cache-Control: public, max-age=60` (`router.py:286`). A feed fetch sends `private, max-age=900` (`router.py:258`). The README states only the feed limit (12 an hour). It also never says that `from_on` is clamped to the location's today, or that `days` is clamped to `days_ahead` (`feeds.py:340`, `public_schedule`).
- [undocumented] `/calendar-feeds*` routes use a bare `require()` (`router.py:203, 210, 219, 228`), so an API key reaches them only to be refused with `403 api-key-not-allowed`. README lines 36-39 describe the keyless routes as self-service and configuration reads, and never mention these. `/portal/calendar-feeds` uses `current_ctx` (`router.py:233`) and is outside the key model entirely.
- [undocumented] `DELETE /calendar-feeds/{id}` is a hard delete with an audit record (`feeds.py:170-174`). It is allowed to the owner, or to a `revoke_any` holder for another person's feed. The README says a manager may "never edit or re-enable" others' feeds, but says nothing about delete. Cancelled bookings, sessions and games are still emitted as events with a cancelled flag (`feeds.py:223, 263, 282`), which the README never says.
- [wording] README line 67 says a team feed "needs a league game key". The code accepts either `leagues.game.manage` or `leagues.result.enter` (`feeds.py:33`, `GAME_READS`). The same check runs on each fetch, so a feed goes empty when the owner loses both keys (`feeds.py:246`).
- [undocumented] `feeds.py` reaches into other contexts' submodules, not just their top-level packages: `platform.staff.principal_for` (:297), `programs.selfservice.portal_list_enrollments` (:272), `scheduling.service.*` and `staff.service.list_my_shifts` (:227), and a new `platform.service.client_identity_is_active` (`backend/app/modules/platform/service.py:551`). CLAUDE.md's boundary rule says a context imports other contexts' top-level package only. Whether `make boundaries` allows it was not run, so this is unverified. The README does not mention these dependencies (it names only `scheduling.service.booking_ids` and `booking_views`).
