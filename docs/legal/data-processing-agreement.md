DRAFT, not legal advice, pending attorney review. Last updated: 2026-11-13.

This Data Processing Agreement (the "DPA") is part of the Terms of Service (the "Terms") between Marvy Labs LLC ("Processor", "Marvy Labs") and the Customer ("Controller"). It applies when Marvy Labs processes Personal Data on behalf of the Customer through Courtmastr Facility. Capitalized terms not defined here have the meaning in the Terms. If this DPA conflicts with the Terms on personal data, this DPA controls.

## 1. Definitions

1.1 "Personal Data" means information relating to an identified or identifiable individual that is Customer Data and that Marvy Labs processes for the Customer.

1.2 "Data Protection Laws" means the privacy and data protection laws that apply to the processing, as they apply to each party.

1.3 "Controller" includes "business"; "Processor" includes "service provider" and "contractor"; "process", "data subject" and "personal data breach" have the meanings those laws give them.

1.4 "Security Incident" means a confirmed breach of security leading to the accidental or unlawful destruction, loss, alteration, unauthorized disclosure of, or access to, Personal Data in Marvy Labs's custody.

1.5 "Sub-processor" means a third party engaged by Marvy Labs that processes Personal Data.

## 2. Roles and scope

2.1 For End User Personal Data, the Customer is the controller (or business) and Marvy Labs is the processor (or service provider). For Customer staff account data that Marvy Labs also uses to secure the Service and for billing and support, Marvy Labs acts as an independent controller as described in its Privacy Policy.

2.2 The subject matter, nature, purpose, duration, data types and data subjects are in Annex 1.

2.3 Duration: the Term of the Terms, plus the time needed to return and delete data under Section 11.

## 3. Customer instructions

3.1 Marvy Labs will process Personal Data only on the Customer's documented instructions, which are the Terms, this DPA, the Customer's configuration of the Service, and its reasonable written requests that are consistent with the Service, unless the law requires otherwise (in which case Marvy Labs will tell the Customer first where lawful).

3.2 Marvy Labs will tell the Customer if it believes an instruction violates Data Protection Laws, and may suspend the instruction until resolved.

3.3 The Customer is responsible for the lawfulness of the processing it instructs, for its notices, for having a valid legal basis, and for parental or guardian consent for children.

## Annex 2: Technical and organizational measures

These are the measures in place or enforced by the product design as of the date above, taken from the Security Baseline and operations documents. "Not yet" lists what is not in place.

**Tenant isolation.** Every table holds the tenant's identifier. Row-level security is forced in PostgreSQL. The application connects as a restricted database role that does not own the tables and cannot bypass row-level security. Automated tests generated per table and per route check cross-tenant access. Requests for records outside the caller's tenant or location return "not found".

**Access control.** Role-based permissions checked at the route and again in the service layer. Deny by default, enforced by an automated test that walks every route. Separate response schemas for staff, member portal and kiosk surfaces. Optional per-user IP allow-lists for staff.

**Authentication.** Passwords stored hashed with Argon2id. Minimum length 12, common-password check. Multi-factor sign-in (time-based one-time passwords with recovery codes), required for privileged roles under the default tenant policy. Step-up re-authentication within the last 10 minutes for sensitive actions. Server-side sessions in secure, HttpOnly cookies, with protection against cross-site request forgery. Sign-in link and reset tokens are single-use, short-lived and stored hashed. Optional single sign-on by OpenID Connect for staff.

**Audit trail.** Mutating actions, sign-ins, permission changes, exports and data-subject requests are written to an append-only table in the same transaction as the change, with actor, time, action and a record of changed fields. Personal data values are stored only as "changed" flags. Retention 24 months online, longer for a defined class.

**Encryption.** In transit: TLS 1.2 or higher at the edge with HSTS. The application refuses to start outside development with database and cache connections that are not verified TLS. [TO CONFIRM: verified in the deployed environment.] At rest: volume-level encryption of the database, cache snapshots, object storage and backups through the hosting provider is the design. [TO CONFIRM: enabled and verified in the deployed AWS environment.] Application-level AES-256-GCM encryption for sensitive form values, medical notes, one-time-password seeds and integration credentials, using one platform key. Not yet: per-tenant keys, a key management service wrapping tenant keys, and a supported key rotation process.

**Payment data.** Card entry only in fields hosted by Stripe. No full card numbers, security codes or full bank account numbers are stored. Payment webhooks are signature-verified and replay-safe. Not yet: a service-provider attestation for the card industry standard, and (to be confirmed) a detector that rejects card numbers typed into free-text fields.

**Uploads.** Files are scanned by an antivirus scanner that must be present outside development, images are re-encoded and metadata stripped, size limits apply, and downloads use short-lived signed links issued after a permission check.

**Secrets.** Platform secrets are supplied from the environment and never stored in the code or images. The application refuses to start in production with example secrets. Integration credentials are encrypted.

**Logging.** Structured logs carry technical identifiers and are intended to exclude personal data, secrets and request bodies. [TO CONFIRM: a redaction filter and test are being completed; log contents not yet verified for personal data.]

**Backups and recovery.** Encrypted database backups, a restore script that checks integrity and role grants, and a restore drill script that restores the newest backup into a scratch database and checks migration state, row counts and row-level security. Object storage uses provider versioning. Not yet: a stated recovery time or recovery point objective, and scheduled backups in a deployed environment. [TO CONFIRM.]

**Data minimization and retention.** Scheduled purges of sessions, tokens, idempotency keys, outbox records and expired audit rows; export files expire. Message-body and provider-payload purges as described in the Privacy Policy. [TO CONFIRM: all purges verified.]

**Application security.** Input validation on all requests, parameterized database access, CSP and other security headers, rate limiting, a web application that loads no third-party scripts except Stripe's, and no advertising or analytics software in the web or mobile apps. Dependency scanning is planned in the pipeline. [TO CONFIRM: scanning status.]

**Organizational.** Access to production is limited to Marvy Labs personnel who need it. Operator access to the Service uses a single shared token today, not per-person accounts. Not yet: per-person operator identity with multi-factor sign-in, a support console, named audited support access, security awareness training, a penetration test, SOC 2 or similar attestation, tamper-evident audit logs. [TO CONFIRM: each of these.]
