A first call returns the token once, a repeat call returns status with `token` and `path` null (`sharing.py:65-66`), and regenerate is the only way to get a new token. - [undocumented] The erasure precheck (`subject.py:37-46`) blocks on a non-cancelled booking ahead where the client is the booking's client or a `BookingParticipant`. The README covers the block (lines 146-147). Not covered: the code is `upcoming-booking` with one generic detail ("The client still has a booking ahead."), so staff cannot tell an own booking from a shared one. If the erased client is the organiser, the participants stay on a booking the precheck already blocked.
- [undocumented] `_export` (`subject.py:25-34`) adds `shared_bookings` with `booking_id` and `attendance` per participant row. The README (line 149, "erasure keeps rows") does not say the subject export includes shared bookings, nor that `_erase` clears notes only on the client's own bookings.
- [wording] The README (line 153) says merge "Needs `update_series` on both bookings". The code checks the target via `_own` and the other via `_authorize` (`service.py:2183,2189-2191`). A caller whose location scope excludes the other booking gets a 422 "No booking has that number." first (`service.py:2184-2188`), so the second check never gives a 403 or 404 for scope.
- [wording] The README (line 152) says merge refuses "blocks and cancelled bookings". The code raises `invalid-state-transition` only when this booking is a block or either is cancelled (`service.py:2196`). A block on the other side is caught earlier as `merge-mismatch` because `kind` differs. The `series-run-in-progress` check (`service.py:2200-2207`) comes after the locks and the mismatch checks, so a mismatched pair reports `merge-mismatch` first. It looks only at series that exist before the merge and only at runs in `pending` or `running`, and reads the runs without locking them, so a run started between the check and the commit is not excluded. Source series runs are re-pointed to the target (`service.py:2241-2244`), which the README never mentions. The audit sentence (line 157) omits the rows for the emptied source series (`merged_into`) and for the target series (`service.py:2253-2262`).
- [undocumented] Merge locking details beyond README lines 153-156: the other booking is found by `booking_number` before any lock (`service.py:2173`), then the pair is re-checked against the ids and series ids read at lock time (`service.py:2198-2199`) with 409 `invalid-state-transition` and the message "The bookings changed while linking; try again." (code named in the README, message not). A number that matches no booking skips the other's series locks and fails later as 422.
- [undocumented] The location-archive guard is now in the README (lines 50-52). Remaining edges: the boundary is `starts_at > now`, so a booking in progress or starting exactly now does not block (`service.py:985`). Only `booking` rows of that location count. Series occurrences not yet generated (a pending or running `generate` run), slot offers and availability windows are not checked, so a location with an offer or a series still generating can be archived and the worker then books at an inactive location. A tentative hold with a null `expires_at` never blocks (the comparison is NULL, `service.py:983`). The check takes no lock and runs inside platform's archive transaction (`platform/service.py:272-273`), so a booking created between the check and the commit is not excluded.
- [contract] `platform/README.md:48` still says scheduling refuses "while a confirmed booking is still to start". The code also refuses on a live tentative checkout hold (`service.py:983`; test `test_a_live_checkout_hold_blocks_archiving_until_it_expires`). The scheduling README now says so, the platform README does not.
- [contract] The guard's 409 body is a bare `Conflict` with a fixed sentence and no `extra` (no count or first booking), so staff cannot see which bookings to cancel. The contract documents only the code in `x-problem-codes` (`openapi-core.yaml:700`). The README does not say staff must cancel or move the bookings through the calendar first.
