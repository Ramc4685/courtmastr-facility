Post-billed behaviour not (or wrongly) described in the README

- [drift] The close and the preview still disagree about credit-backs. `_plan` builds a line for a package with only a restored credit and no new usage with `rate = None` and `skipped_reason = "no-usage"` (`postbilled.py:214`, `:223`). The preview shows total 0, but a real close acts on it (`_run` adds a credit step when `line["credits"]`, `:310-311`). The `preview_close` docstring now admits "credit-backs are not shown" (`:255`), but the README still says the preview "shows the same lines without writing", and `PostBilledPreviewLineOut` has no field for the pending credit-back.
- [drift] A credit-back writes no line and no total. `_credit_back` adjusts or reverses the original line's charge (`:365-369`) and stamps `credited_at`, but `post_billed_line.total_minor`, `session_count` and the old close's `total_minor` are unchanged. `PostBilledLineOut` has no field for credited sessions; the only trace is the audit record `credited_sessions` (`:372-373`). README says only that the charge is adjusted.
- [drift] `post_billed_line.charge_id` is rewritten when the charge is adjusted (`:367`). When the charge is reversed, `charge_id` and `invoice_id` still point at the reversed charge. When staff already changed it by hand (`:363`), the line keeps its old `charge_id`. A line with a null `charge_id` (a tier priced at 0) is credited back with no billing call (`:362`, `:364`) and its usage row is still stamped. None of this is documented.
- [drift] The by-hand test is narrow: `charge.status != "active" or charge.kind == "reversal"` (`:363`). An active charge that staff edited by hand to a different quantity is still adjusted from its current quantity (`left = charge.quantity - len(rows)`, `:365`), so "changed by hand" in the README covers only reversed or non-active charges in practice. The audit key `charge_changed_by_hand` is only in the README, not the code comment of the model.
- [drift] Failure capture is still partial. `_run` catches only `DomainError` and `IntegrityError` (`:318`). Any other exception aborts the whole close and the `post_billed_close` row added earlier goes with it, so "failures are kept on the close" holds for those two kinds. `code` falls back to the literal `conflict` for an `IntegrityError` (`:319`). The README does not list the possible `code` values. When a package fails in both steps, `setdefault` keeps only the first code (`:319`).
- [drift] Retry edge cases not described. `retry_close` re-plans only the failed ids (`:335`); a failed package that no longer has anything owed or restored is not in the plan, so it silently drops out of `failures` with nothing done (`:341`). Retry bills usage up to the original `closing_on` only (usage after it waits for a later close), and the line it creates belongs to the old close, whose `package_count`, `session_count` and `total_minor` are increased (`:342-344`). A package that already has a line at this close gets only its credit-back re-run (`:336-340`). A repeat `POST /post-billed-closes` on the same date never retries; only the new route does. Retry on a close with no failures returns it unchanged (`:333-334`). README documents the route but none of this.
- [drift] "Ended packages with nothing owed are neither read nor locked" is looser in code. `unbilled` counts any unbilled consumed usage regardless of date (`:185-191`), so an ended package whose only usage is dated after `closing_on` is selected and `FOR UPDATE` locked (`:205`), then dropped by the later filter (`:209`). The README says "owed", but owed here means "owed at some date", not "owed at this close".
- [drift] A package without auto-renew is ended by moving the `valid_during` end to `max(lower, closing_on) + 1 day` and calling `service._expire` (`:408-412`). The window rewrite, the audit and the `PackageExpired` event are not described. The README rule "nothing is held and nothing was used after the closing date" is implemented as "no reserved credits and no unbilled usage of any date" (`:408`, `_usage(..., date.max, ...)`). The check runs only inside `_bill`, so a package with no new usage at this close, or one whose bill step failed, is never ended at that close.
- [drift] `_plan` picks up a package when it is active or has unbilled usage or a pending credit-back, whatever its status (`:199-202`). The module docstring says held credits are "reported as unsettled" (`:8`), and `unsettled_count` is the package-wide `sessions_reserved_count`, not only holds on or before `closing_on` (`:220`). The README does not mention the preview field or this scope.
- [wording] The router docstring and `preview_close` summary still say "Every open post-billed package at the location" (`router.py:282`). They also cover ended or removed packages with usage or a pending credit-back.
- [undocumented] No invoice is created when the charge total is 0 (`:392`), so `invoice_id` stays null. README says each package gets "one `create_invoice_for_charges`".
- [undocumented] A usage row is reused when a credited source is used again: one `post_billed_usage` row per source, repointed to the new line with `credited_at` cleared (`:398-404`, unique key `uq_post_billed_usage`). The history of the earlier line is overwritten on that row.
- [undocumented] `credited_at` is a model and migration column (`models.py:583`, migration `1481`) but is not in any response schema or in `docs/architecture/data-model-people.md`. That document still says PKG-11 has "no columns reserved" (lines 1097 and 1719), so none of the four `post_billed_*` tables are in the schema of record; the `failures` JSONB column is the same.
- [undocumented] Rates. `GET/POST /post-billed-rates` and `PATCH /post-billed-rates/{id}` (`router.py:263-277`, gate `packages.plan.manage`, `postbilled.py:61-88`). The base-tier check runs on create and update only for active tiers and only when some tier exists (`:91-98`), so a reservation type with no tiers is allowed until the first one is added, and that first one must be `min_sessions = 1`. Rate uniqueness (`uq_post_billed_rate_tier`, code `rate-tier-exists`, `:47`) is not in the README. Rates that existed before with no tier 1 are not migrated or flagged, so `_tier` can return no rate (`skipped_reason = "no-rate"`, `:223`), contrary to the README "every used session has a rate".
- [undocumented] Rates are not checked against a location: `create_rate` has no reservation-type location lookup (`:71-78`), while the package sale does (`:118`). A rate can be set for a reservation type of any location of the tenant.
- [undocumented] `register_type_location` must be called at startup; otherwise `open_package` raises `RuntimeError` (`:116-117`) rather than a domain error. Only `app/bootstrap.py:70` wires it, so any app built without bootstrap fails on opening a post-billed package. A reservation type that does not exist and one of another location give the same 422 (`:118`).
- [undocumented] `open_package` details: sale gate is `packages.package.sell` at the location, not a post-billed key; `share_with_related`, `is_autopay` and `is_auto_renew` inputs; default name "Post-billed sessions"; `invoice_mode = none`; sales channel `staff` (`:111-140`).
- [undocumented] Renewal of a post-billed package ignores `renews_as_plan_id` and a source contract plan (`service.py:923-924`), so it can never switch to a plan. The copy list includes `billing_mode` (`service.py:943`). README says only "A renewal stays post-billed".
