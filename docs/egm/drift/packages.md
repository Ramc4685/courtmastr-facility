Recent change (`_credit_back`, `_live_charge`, `_clear_stale_failures`): edge cases the README does not state

- [drift] The kept discount is an absolute amount, not scaled: `min(charge.discount_minor, left * charge.unit_price_minor)` (`postbilled.py:398`). Crediting back 2 of 4 sessions keeps a 40 minor-unit discount whole while the gross halves, until it hits the cap. README says only "kept, capped at the new gross".
- [drift] `_live_charge` picks the newest live charge by `max(c.id)` (`postbilled.py:381`). That relies on ids ordering by creation (UUIDv7). If a line has several live charges (the code allows it) only the newest is adjusted and the others are left untouched. README says "the live charge" in the singular.
- [drift] `_live_charge` excludes only `reversal` kind and non-`active` status (`:378-380`). A charge staff edited to a different quantity or price is adjusted from its current quantity (`left = charge.quantity - len(rows)`, `:396`). "Changed by hand" (README, audit key `charge_changed_by_hand`, `:406`) therefore means only "no live charge left"; a hand edit that is still live is followed, not flagged. The audit change for the follow case does not record that a replacement was used.
- [drift] `post_billed_line.charge_id` is rewritten to the replacement on an adjust (`:399`). On a reverse, or when no live charge is left, `charge_id` and `invoice_id` keep pointing at the old charge. A line whose charge was never set is handled as "no live charge" and audited as `charge_changed_by_hand` (`:406`), which is misleading there. Not documented.
- [drift] Credit-back writes no line and no totals: `post_billed_line.total_minor`, `session_count` and the old close's `total_minor` are unchanged; the only trace is the audit record `credited_sessions` (`:406-407`). README says only that the charge is adjusted.
- [resolved] `_clear_stale_failures` now counts a package as handled only when this run gave it a step (credit-back or billing) and it did not fail; a line with no step, or skipped with `no-rate`, no longer clears an earlier close's failure. Each edited close gets an audit record (`cleared_failures`, `by_close`).
- [drift] `_clear_stale_failures` runs in `retry_close` as well (`:360`), excluding the retried close only. A retry therefore also edits the `failures` of other closes of the location, and so does a normal close; the README mentions only the later-close case.
- [undocumented] Clearing another close's `failures` is not audited and does not touch that close's totals (`:338-341`); it takes `FOR UPDATE` on every close of the location with failures, in `id` order, after the package locks, so concurrent closes of one location contend on those rows. Not mentioned in the README.
- [undocumented] A repeat `POST /post-billed-closes` for an existing date returns before `_plan` and never clears stale failures (`:275-276`); only a new close or a retry does.

Post-billed behaviour not (or wrongly) described in the README

- [drift] The close and the preview disagree about credit-backs. `_plan` builds a line for a package with only a restored credit and no new usage with `rate = None` and `skipped_reason = "no-usage"` (`:214`, `:223`). The preview shows total 0, yet a real close acts on it (`_run` adds the credit step when `line["credits"]`, `:312-313`). The `preview_close` docstring admits "credit-backs are not shown" (`:255`); the README still says the preview "shows the same lines without writing".
- [drift] Failure capture is partial. `_run` catches only `DomainError` and `IntegrityError` (`:320`). Any other exception aborts the whole close and the `post_billed_close` row goes with it. `code` falls back to the literal `conflict` for an `IntegrityError` (`:321`). When a package fails in both steps, `setdefault` keeps only the first code. The possible `code` values are not listed.
- [drift] Retry edge cases. `retry_close` re-plans only the failed ids (`:353`); a failed package with nothing owed or restored is not in the plan, so it drops out of `failures` with nothing done (`:359`). Retry bills usage only up to the original `closing_on`, and the new line belongs to the old close, whose `package_count`, `session_count` and `total_minor` grow (`:361-363`). A package that already has a line at this close gets only its credit-back re-run (`:354-358`). A retry publishes no event, so `packages.post_billed.period_closed` is not sent for its added lines. Retry on a close with no failures returns it unchanged (`:350-352`).
- [drift] "Ended packages with nothing owed are neither read nor locked" is looser in code. `unbilled` counts any unbilled consumed usage regardless of date (`:185-191`), so an ended package whose only usage is dated after `closing_on` is selected and locked `FOR UPDATE` (`:205`), then dropped by the later filter (`:209`). The README test "nothing owed" means owed at any date, not at this close. The `test_a_close_reads_only_packages_with_something_owed` test does not cover that case.
- [drift] A package without auto-renew is ended by moving the end of `valid_during` to `max(lower, closing_on) + 1 day` and calling `service._expire` (`:443-446`); the window rewrite, audit and `PackageExpired` event are not described. The README rule "nothing is held and nothing was used after the closing date" is implemented as "no reserved credits and no unbilled usage of any date" (`:442`, `_usage(..., date.max, ...)`). It runs only inside `_bill`, so a package with no new usage at this close, or whose bill step failed, is never ended at that close.
- [drift] `_plan` picks up a package when it is active or has unbilled usage or a pending credit-back, whatever its status (`:199-202`). `unsettled_count` is the package-wide `sessions_reserved_count`, not only holds on or before `closing_on` (`:220`). The README does not mention the preview field or this scope.
- [wording] The router docstring and summary still say "Every open post-billed package at the location" (`router.py:282`); the code also covers ended or removed packages with usage or a pending credit-back.
- [undocumented] No invoice is created when the charge total is 0 (`:426`), so `invoice_id` stays null. README says each package gets "one `create_invoice_for_charges`".
- [undocumented] A usage row is reused when a credited source is used again: one `post_billed_usage` row per source, repointed to the new line with `credited_at` cleared (`:432-440`, unique key `uq_post_billed_usage`). The earlier line's link on that row is overwritten.
- [undocumented] `credited_at` is a model and migration column (`models.py:583`, migration `1481`) but is in no response schema and not in `docs/architecture/data-model-people.md`, which still says PKG-11 has "no columns reserved" (lines 1097 and 1719). None of the four `post_billed_*` tables, nor `failures` (`models.py:540`), are in the schema of record.
- [undocumented] Rates. `GET/POST /post-billed-rates` and `PATCH /post-billed-rates/{id}` (`router.py:263-277`) are gated by `packages.plan.manage` (`postbilled.py:61-88`), which the README does not say. The base-tier check runs only for active tiers and only when some tier exists (`:91-98`), so a type with no tiers is allowed until the first tier is added, and rates that existed before with no tier 1 are not flagged, so `_tier` can return None (`skipped_reason = "no-rate"`, `:223`), contrary to the README "every used session has a rate". `uq_post_billed_rate_tier` (code `rate-tier-exists`, `:47`) is not in the README.
- [undocumented] `create_rate` does not check that the reservation type belongs to a location (`:71-78`), while the package sale does (`:118`).
- [undocumented] `register_type_location` must be called at startup; otherwise `open_package` raises `RuntimeError` (`:116-117`), not a domain error. Only `app/bootstrap.py:70` wires it. A nonexistent type and one of another location give the same 422 (`:118`).
- [undocumented] `open_package` details: gate is `packages.package.sell` at the location (`:114`), not a post-billed key; extra inputs `share_with_related`, `is_autopay`, `is_auto_renew`; default name "Post-billed sessions"; `invoice_mode = none`; sales channel `staff` (`:111-140`).
- [undocumented] Renewal of a post-billed package forces `plan_id = None`, so it ignores `renews_as_plan_id` and a source contract plan and can never switch to a plan (`service.py:923-924`); the copy list includes `billing_mode` (`service.py:943`). README says only "A renewal stays post-billed".
