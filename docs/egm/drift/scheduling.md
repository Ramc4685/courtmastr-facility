Phase 15 additions

- [undocumented] `service.get_sessions(session, session_ids) -> dict[UUID, dict]` (`service.py:861-864`) is not in the README "Interface for other contexts" block. It returns session views by id in one read, leaves unknown ids out, applies no status or location filter (a cancelled session comes back with `status: "cancelled"`), and takes any iterable (empty gives `{}`). Callers: `programs/selfservice.py:306`, `integrations/feeds.py:300`.
- [undocumented] `booking_ids` is documented as `booking_ids(*, client_id=None, status=None, ...)` (README line 33). The code also takes `client_ids`, `series_id`, `resource_id`, `starts_from`, `starts_to` (exclusive upper bound) and `location_id` (`service.py:931-941`). It has no `ORDER BY`. `integrations/feeds.py:399` applies `.limit(MAX_EVENTS)` and only then drops cancelled and already-shown bookings, so the public schedule's busy list is an arbitrary subset when a location has more than 1000 bookings in the window, and cancelled rows eat into that cap.
- [undocumented] `session_window` has its signature in the README (line 35) but not its result rule: confirmed and `is_self_bookable` sessions only, ordered by booking start then session id, capped at `limit` (default 500), `location_id` matched on `Session.location_id` (`service.py:1018-1043`). A session that is not self-bookable never reaches `programs.selfservice.public_seats`, so the public schedule omits a direct-link-only or staff-only session.
- [stale] README "Not built" (lines 121-125) says calendar feeds (SCH-19) and the public schedule (SCH-20: `getPublicSchedule`, `getPublicScheduleSettings`, `updatePublicScheduleSettings`) are not built. Phase 15 built them in `integrations/feeds.py` (`integrations/README.md:113`, `:198`), reading through `scheduling.service.booking_ids`, `booking_views` and `programs.selfservice.public_seats`. The scheduling README and `openapi-core.yaml` (tag `scheduling`) do not say they are served by integrations, and the `scheduling.public_schedule.manage` key (`permissions.py:42`) is described as unused by any route.
- [undocumented] The `events.py` row (line 17) names rentals, leagues, engagement, programs and packages as subscribers but not integrations, which subscribes to `scheduling.booking.rescheduled` and `scheduling.session.cancelled` (`integrations/README.md:193-194`). Integrations also reads `get_session`, `get_sessions`, `booking_views` and `booking_ids` (`integrations/meetings.py:90,219,279`; `feeds.py:300,399`), which the README does not list as callers.

Carried from main (re-verified, line numbers updated)

The four participant routes (`router.py:368-387`) are in no `docs/api/*.yaml`. - [contract] `resolveDirectLink` (`openapi-core.yaml:3460`) is `GET /public/direct-links/{token}` with the token in the path, recorded as an accepted exception to "no secrets in URLs". The code serves `POST /public/direct-links/resolve` with the token in the body (`router.py:355`); the exception text is stale. The contract says it resolves "its session or slot offer", but `sharing.resolve_link` (`sharing.py:82-95`) queries `Session` only, and it resolves until the booking ends (`booking.ends_at <= now`, line 87), not only "while ahead" as the README says.

The path parameter is `schedule_session_id` in the code and `session_id` in the contract.

Audit records `is_direct_link_active` and `token_rotated`, never the token (`sharing.py:51`); `token_rotated` is always `True`, even on revoke. `DirectLinkChanged` also fires on regenerate with `is_active` true, indistinguishable from a first turn-on. `create_link` and regenerate refuse a cancelled session with `invalid-state-transition` (`sharing.py:63-64`).

- [undocumented] The interface block omits `service.reservation_type_location(session, reservation_type_id) -> UUID | None` (`service.py:990`, wired from `bootstrap.py` into packages; returns None where `type_location` at `service.py:1010` raises NotFound), `has_live_link` (`service.py:843`, named only in a bullet), `merge_series` (`service.py:2183`, takes a principal) and `hours_warnings`.
- [undocumented] The events `scheduling.session.direct_link_changed`, `scheduling.participant.added`, `.removed`, `.attendance_marked` and `scheduling.series.merged` (`events.py`) are missing from the README `events.py` row, which lists ten.
- [undocumented] Participant edges: `add_participant` refuses a cancelled booking and a block (`sharing.py:103-104`), `remove_participant` refuses the organiser (`:195-200`), `mark_attendance` refuses a cancelled booking, all with `invalid-state-transition`. The organiser's row is audited and published as `participant.added` when first listed, under the `enrollment.create` key. The README says "Gates reuse the enrolment and attendance keys" without naming `enrollment.create`, `enrollment.cancel`, `attendance.mark` and `mark_exception`; link create, regenerate and revoke all share `registration_link.create` (`permissions.py:39`), so revoke has no separate gate.
- [undocumented] Erasure precheck (`subject.py`): the block is `upcoming-booking` with one generic detail, so staff cannot tell an own booking from a shared one, and nothing removes a participant on an erasure's behalf (`remove_participant` needs `enrollment.cancel` and refuses the organiser). `_export` adds `shared_bookings`; the README does not mention it, nor that `_erase` clears notes only on the client's own bookings.
- [wording] README says merge "Needs `update_series` on both bookings". The code checks the target via `_own` and the other via `_authorize` (`service.py:2199,2208-2210`); a caller whose location scope excludes the other booking gets 422 "No booking has that number." first. README says merge refuses "blocks and cancelled bookings"; the code raises `invalid-state-transition` only when this booking is a block or either is cancelled, and a block on the other side is caught earlier as `merge-mismatch`.
- [undocumented] Merge: the `series-run-in-progress` check reads runs without locking them, only for series existing before the merge and only in `pending` or `running`, so a run started between the check and the commit is not excluded. The source series' runs are re-pointed to the target and its rules renumbered after the target's, and the audit also records `merged_into` for the emptied source and `merged_booking_numbers` and `merged_count` for the target (`service.py:2245-2290`). The README names none of these.
- [undocumented] Location-archive guard: the boundary is `starts_at > now`, so a booking in progress does not block; only `booking` rows of that location count (series not yet generated, slot offers and availability windows are not checked); a tentative hold with null `expires_at` never blocks; no lock is taken (`service.py:995-1007`). The 409 is a bare `Conflict` with no count or first booking.
