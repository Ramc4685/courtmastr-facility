## backend/app/modules/integrations/README.md

Fresh report, 2026-11-13, on `claude/phase15-public-api-integrations` (working tree, including the uncommitted INT-09 work: `meetings.py`, `ports/video_meeting.py`, `adapters/video.py`, migration 1703, and the QuickBooks security fixes in migration 1702). Read-only, no tests run. Paths are under `backend/app/modules/integrations/` unless they start with `docs/`, `config/`, `web/` or `backend/`. README line numbers are the working-tree README (149 lines). Contract line numbers are `docs/api/openapi-programs.yaml`.

Dropped since the last report because the code or README now matches: the QuickBooks `status_url` 404 (now the flat `GET /accounting-exports`, `quickbooks.py:311`), `connected_at` on a pending connection (`service.py:662`), the cross-kind posting-key collision (`quickbooks.py:259-263`), the webhook trusting the simulated adapter's public secret (`quickbooks.py:340`), the silent realm routing (`app.claim_provider_account`, `quickbooks.py:164`, migration 1702; disconnect releases it, `service.py:697-707`), the stale adapter, port and router docstrings, the "`sync_from`/`auto_sync` stored but unread" and "no `mappings-incomplete` / sub-category inheritance / `needs_reauth`" items (README lines 141-142 now say so), the reconnect `409` (README lines 139-140), and the `run_sync` 31-day cap (README line 131); and, for INT-09, the repeat `PUT` on a changed connection or with a new host (now dropped and recreated, `meetings.put_meeting`), meetings left joinable after a Zoom disconnect (now marked `failed`, `meetings.on_disconnect`), staff `PUT` on a cancelled or finished session (now `409 invalid-state-transition`), and the adapter directory's fixed Zoom text (now reports `zoom` connected or `not_configured`).

### INT-07 QuickBooks Online

- [contract] Deliberate deviation, written down in the README (lines 63-66). `completeExternalConnectionOAuth` is an anonymous `GET` (`security: []`, `x-permission: oauth-state`) with `state`, `code`, `realm_id`, `error` in the query and answers `302` (openapi-programs.yaml:6745-6770). The code serves `POST /external-connections/oauth/callback`, a staff route gated by `integrations.connection.manage` that also needs a signed-in person, with a JSON body, and answers `200 {external_connection_id, status, return_url}` (`router.py:159-167`, `schemas.py:174-186`). The yaml still describes the old shape. It also types `realm_id` as `format: uuid`, but the code takes digits only (`schemas.py:177`).
- [contract] Path parameter is `connection_id` in the contract for every `/external-connections/{connection_id}...` operation (openapi-programs.yaml:6771, 6811, 6834, 6875, 6912) and `external_connection_id` in the code (`router.py:170-227`). Same URL, different name in the generated spec and in `web/src/api/schema.d.ts`.
- [contract] `ExternalConnection` response. The contract returns `granted_scopes`, `settings`, `updated_at` and `authorize_url` "while pending" (openapi-programs.yaml:9085-9107). `ExternalConnectionOut` has none of the first three (`schemas.py:127-137`) and `authorize_url` exists only on the create response (`schemas.py:140-141`, `router.py:156`). A pending link cannot be fetched again and patched settings cannot be read back; `return_url`, `mappings`, `account_map` and `class_map` live in that same `settings` blob (`quickbooks.py:112, 267`).
- [contract] `createExternalConnection`. The contract documents `409 connection-exists` and `422 provider-not-available` (openapi-programs.yaml:6742-6744). Code: `provider` is a three-value `Literal` of `accounting_file`, `quickbooks_online`, `zoom` (`schemas.py:118`), so any other provider (the contract's enum also lists smartwaiver, perkville and more, openapi-programs.yaml:9094) is a generic validation 422 and `accounting_file` is in the code but not the contract enum; QuickBooks with the flag off is `422 provider-not-configured` (`service.py:653-656`), not listed; a duplicate (provider, location) hits `uq_external_connection` (`models.py:137-139`) and returns the generic `409 already-exists`. The body also accepts `zoom` (the tenant's Server-to-Server app) and `settings` (`schemas.py:119-123`), which the contract schema lacks (openapi-programs.yaml:9109-9116).
- [contract] `updateExternalConnection` says settings are "sync_from date, sync mode (invoice or daily summary), auto-sync flag" and the body is `application/merge-patch+json` (openapi-programs.yaml:6803, 9120-9124). The code accepts `default_income_account`, `sync_from`, `auto_sync` (`quickbooks.py:37`); there is no sync mode, and `sync_from` is an unvalidated string (`schemas.py:144-147`).
- [contract] `runSync` is a job that "creates or retries the accounting_export row of each location and day in the range" and answers an `Accepted` handle (openapi-programs.yaml:6919-6940). The code runs in the request (README line 131 says so) for one location (`quickbooks.py:287`), returns `{status: "completed", counts, status_url}` (`schemas.py:193-196`), takes `location_id` which the contract's `SyncRun` lacks, and has no `local_kinds` (`schemas.py:167-172`; contract openapi-programs.yaml:9170-9176). `mappings-incomplete` (422) is never raised: an unmapped QuickBooks key fails that day with a plain validation message (`service.py:808-809`), a revenue key with a default income account posts with a warning (:803-805).
- [contract] `listAccountingExports` is not served at its contract path (openapi-programs.yaml:6875). The flat route that is served lacks the `business_on[gte]`, `business_on[lte]` filters and the `status[in]` form (`router.py:230-233`, filter fields in `service.py:833-836`).
- [contract] `AccountingExport` response. The contract has `supersedes_export_id`, `created_at`, `updated_at` (openapi-programs.yaml:9157-9161). `AccountingExportOut` has none (`schemas.py:205-216`) and the model has no `supersedes_export_id` column (`models.py:157-185`).
- [contract] `SyncMapping` and `SyncMappings`. The contract has an `id` per mapping and a `sync_mapping` table (openapi-programs.yaml:9126-9135). The code returns no `id` (`schemas.py:150-166`) and keeps the list in `external_connection.settings["mappings"]` (`quickbooks.py:267`). The README admits the missing table (lines 126-127); the contract does not know. `external_options` is `{accounts, classes}` of `{id, name}` (`quickbooks.py:237-243`), which the contract leaves unspecified.
- [contract] `receiveQuickBooksEvents` documents `200 No content` and a `429` (openapi-programs.yaml:6964-6980). The code returns `200 {"stored": n}` (`router.py:215-220`, `schemas.py:189-190`) and neither it nor the OAuth callback has a `rate_limit` dependency (only `/public/schedule` does, `router.py:377`).
- [undocumented] What `local_key` must be. The contract and ADR 0012 say "tax id", "revenue category id" (openapi-programs.yaml:9131, adr/0012:158-166). The export looks mappings up by posting key: `revenue:<category id>`, `tax_payable:<tax id>`, or the bare ledger account name (`domain/journal.py:18-23`, `service.py:802`). A mapping saved with a raw category id never matches. README lines 80-81 mention that posting keys are unique across kinds but not that `local_key` must be one; `unmapped` lists the posting keys (`quickbooks.py:249`), the only hint.
- [undocumented] ADR 0012 refresh rules the README does not list as not built (its lines 141-142 name only `needs_reauth`). A refresh failure (`invalid_grant`) emits no `integrations.connection.failed` and notifies no Owner, rotation is not stored under a row lock (adr/0012:155-158; `quickbooks.py:90-92` lets the exception propagate, `events.py` has only the webhook-disabled event), and `ExternalConnection.failure_count` is never written (`models.py:154`).
- [undocumented] `getSyncMappings` and every call that needs the access token can refresh and reseal credentials (`quickbooks.py:82-92`, called at :240), so a `GET` writes. The README rationale for a POST callback ("no mutating GET", lines 65-66) does not mention it. The request transaction commits, so the rotated token is kept.
- [missing] The OAuth round trip cannot complete in a browser. README lines 63-64 say the provider sends the browser to the web page `/integrations/quickbooks/callback`, which POSTs to the API. No such page exists: `web/src` mentions it only in the generated `schema.d.ts`. The default `return_url` `{web_base_url}/setup/integrations` (`quickbooks.py:112`) has no page either, and `FakeQuickBooks.authorize_url` redirects to the callback page too (`adapters/accounting.py:101-102`).
- [undocumented] `run_sync` rules the README leaves out (its line 131 gives only the 31-day cap): days already `failed` are counted as `failed` and not retried unless `retries_failed` is true (`quickbooks.py:303-304`); today and future days are refused (`last >= today`, :292); a body `location_id` is ignored when the connection has its own (:287).
- [stale-not-built] `docs/status/16-integrations.md:22` says INT-07 lists "OAuth per location, the class/account mapping table and screen" as not built and the export runs only through `POST /accounting-exports`. The OAuth round trip, mappings, settings, sync, retry and webhook now exist (the table and screen do not). Line 24 says INT-09 has only the simulated adapter and lists "Zoom OAuth ... the entitlement-checked join redirect, and attendance" as not built; a Zoom connection, the session meeting routes, the join and the attendance mark now exist (see below).

### INT-09 Virtual sessions (new)

- [contract] Deliberate deviation, written down in the README (lines 102-105). `joinPortalVirtualSession` is a `GET` answering `302` to the meeting (openapi-programs.yaml:7041-7060). The code is `POST /portal/enrollments/{enrollment_id}/join` answering `200 {join_url, passcode}` (`router.py:322-328`, `schemas.py:274-276`, `meetings.py:217`), because it writes attendance. The yaml says the redirect marks attendance "when the policy says so" and "the raw join URL is never ... listed"; the code always marks (`meetings.py:213-216`) and returns the raw URL and passcode in a response body. The yaml is not updated.
- [contract] Path parameter is `{session_id}` in the contract (openapi-programs.yaml:6981-6983) and `{schedule_session_id}` in the code for all three video-meeting operations (`router.py:301, 306, 316`). - [contract] `VideoMeeting` response and errors. The contract's `status` enum is `pending`, `scheduled`, `failed`, `deleted` and `join_url` is `format: uri` (openapi-programs.yaml:9178-9195); `VideoMeetingOut` has only `scheduled` and `failed` (`schemas.py:261-271`). `failed` with `last_error = connection-disconnected` is written only when the Zoom connection is disconnected (`meetings.on_disconnect`). - [undocumented] Zoom has no feature flag or plan check: any holder of `integrations.connection.manage` can connect it, while `integrations.quickbooks_enabled` guards only QuickBooks (`service.py:653-656`). ### Calendar feeds and public schedule

- [contract] `listCalendarFeeds` declares `x-permission: integrations.calendar_feed.revoke_any` (openapi-programs.yaml:7063). The route is a bare `require()` (`router.py:271`): any staff user lists their own feeds, and `revoke_any` only widens the list to others' feeds in their locations (`feeds.py:63-72`). The README (lines 89-91) matches the code, so the contract differs.
- [contract] `updateCalendarFeed` is summarised as "Change filters, or disable and re-enable" (openapi-programs.yaml:7078). `CalendarFeedUpdate` accepts only `name`, `include_shifts` and `status` (`schemas.py:294`).
- [contract] The nine feed and public-schedule operations carry only a summary and permission, with no parameters, request bodies or response schemas: the staff and portal feed operations (openapi-programs.yaml:7057-7099), `getPublicCalendarFeed` (:7100) and the three public-schedule ones (`docs/api/openapi-core.yaml:3354-3380`). The code requires `location_id` on `GET /public/schedule` and `GET /public-schedule-settings`, and takes `from_on` and `days` (1 to 31) on the first (`router.py:361, 379-382`).
- [contract] The three public-schedule operations are tagged `[scheduling]` in the contract, but the generated spec tags them `['integrations', 'scheduling']`, because router-level `tags=["integrations"]` (`router.py:28`) is added to the per-route `tags=["scheduling"]` (:361, 367, 376).
- [contract] `getPublicCalendarFeed` says the token is "revocable and rotatable from the portal" (openapi-programs.yaml:7106-7108). A member can only create a feed: `POST /portal/calendar-feeds` (`router.py:331`) is the only portal route. Disable, re-enable and delete go through `_manage`, which calls `_staff_only` (`feeds.py:137-138`). Repeated POSTs mint unlimited member feeds (`feeds.py:123-134`, no uniqueness check).
- [stale-not-built] Status docs still say calendar feeds and the public schedule are not built: `docs/status/16-integrations.md:23` (INT-08), `docs/status/02-resources-scheduling.md:46-47` (SCH-19, SCH-20), `docs/status/12-staff.md:29` (STF-13), `docs/status/README.md:97-98`. `backend/app/modules/scheduling/README.md:105-106` lists "public schedule (SCH-20)" and "calendar feeds (SCH-19)" under "Not built".
- [undocumented] The README never names `scheduling.public_schedule.manage`, which gates `/public-schedule-settings` (`router.py:362, 369`; registered at `backend/app/modules/scheduling/permissions.py:42`). The settings write audits as `scheduling.public_schedule.update` (`feeds.py:340`). A GET for a location with no row returns unsaved defaults, not a 404 (`feeds.py:316-333`).
- [undocumented] Public schedule delivery details are missing. `GET /public/schedule` is rate limited as `public-schedule`, 60 a minute per IP (`config/app.yaml:77`), and sends `Cache-Control: public, max-age=60` (`router.py:385`); a feed fetch sends `private, max-age=900` (:357). The README states only the feed limit (12 an hour). It also never says `from_on` is clamped to the location's today and `days` to `days_ahead` (`feeds.py:344-353`).
- [undocumented] The README text (lines 92-95) says published sessions come from `scheduling.service.session_window`, but not that this call is capped at `MAX_EVENTS` = 1000 sessions (`feeds.py:30, 359`), and that with `show_sessions` off a published session is dropped from the sessions list and, when `show_busy` is on, appears as a busy time (`feeds.py:368-369`). The 1000 cap is stated for feeds only (line 143-144).
- [undocumented] `/calendar-feeds*` routes use a bare `require()` (`router.py:271, 278, 287, 296`), so an API key reaches them only to get `403 api-key-not-allowed`. README lines 39-43 name self-service routes and configuration reads as the keyless routes and omit these. `/portal/calendar-feeds` uses `current_ctx` (`router.py:333`) and is outside the key model.
- [undocumented] `DELETE /calendar-feeds/{id}` is a hard delete with an audit record (`feeds.py:170-174`), allowed to the owner or to a `revoke_any` holder for another person's feed. The README says a manager may "never edit or re-enable" others' feeds (lines 90-91) and says nothing about delete. Cancelled bookings, sessions and games are still emitted as events with a cancelled flag (`feeds.py:223, 263, 282`).
- [wording] README line 90 says a team feed "needs a league game key". The code accepts either `leagues.game.manage` or `leagues.result.enter` (`feeds.py:33`, `GAME_READS`), rechecked on each fetch, so a feed goes empty when the owner loses both (`feeds.py:246`).
