## backend/app/modules/engagement/README.md

Refreshed against the working tree as it stands (uncommitted edits included). Line numbers are the current README's (137 lines). Tags: stale-not-built 0, missing 1, contract 5, undocumented 9, wording 3.

- [contract] README:71 says API keys holding engagement scopes can create campaigns. Keys cannot carry engagement permissions: `KEY_CONTEXTS` leaves `engagement` out, and the comment says campaigns "stay with signed-in people" (`backend/app/modules/integrations/service.py:64-72`). The "sender is then empty" case (`service.py:788-790`, `principal.staff_user_id`) is therefore unreachable today.
- [contract] README:34 says suppressions are `T`, admin only. Only create and release are admin only (`router.py:251,256` via `SuppressionAdmin`; `service.py:1113-1121`). `GET /suppressions` needs only `engagement.campaign.read` (`router.py:246-248`; `service.py:1103-1104`), which is an `L` key held by Manager as well as Admin (`permissions.py:12,15`). Managers can list every suppressed address in the tenant.
- [contract] README:58-59 says the context emits `engagement.consent.changed`. It is published only for one-click unsubscribe and the public preference centre (`service.py:1183,1224`). Staff changes (`service.py:198-206`), portal changes (`service.py:222-226`), `import_consent` (`service.py:144-181`) and the GDPR-off opt-outs (`service.py:256-287`) change consent through `_apply` and publish nothing.
- [contract] README:132-137 (Not built) does not list the `engagement`-tagged operations in `docs/api/openapi-programs.yaml` that no route serves (`router.py`, all routes). They are: `POST /webhooks/email/{provider}` (spec :5622; README:92-94 says the webhook is not built, but only as a deviation); `POST /campaigns/{id}/resume` (:4698), `/unschedule` (:5654), `/copy` (:5664) and `/audience-preview` (:5989); `/media-assets*` (:5674, :5689); `/news-stories*` (:5737-5772) and the rest of the app-content, portal-invitation, trial-request, favorites and app-analytics operations. README:134 covers the image library (MKT-06) only.
- [contract] Spec and code disagree on shape for routes the README describes. The spec has `POST /campaigns/{id}/test-send` (`openapi-programs.yaml:4633`); the code serves `POST /campaigns/{id}/test` (`router.py:202`). The spec has `/portal/communication-preferences` (`openapi-programs.yaml:4196`); the code serves `/portal/clients/{client_id}/communication-preferences` (`router.py:51,56`; README:125 matches the code).
- [missing] README:120 lists `locale?` as a field of `POST /portal/devices`. The schema accepts it (`schemas.py:442`) but it is never stored: `DeviceRegistration` has no `locale` column (`models.py:384-410`) and `register_portal_device` never reads it (`service.py:1281-1311`).
- [undocumented] `POST /campaigns/{id}/test` (`router.py:202`, `service.py:916-927`) sends the campaign only to the requesting staff member, as `operational` mail with a `[TEST]` subject. It is gated by `engagement.campaign.edit`, a key the README names only for templates and segments (README:33). Not mentioned anywhere.
- [undocumented] Campaign lifecycle rules beyond README:70. Edit, delete and cancel use `campaign.create` (`service.py:804,819,889`). Delete is draft-only (`service.py:821-822`). Cancel is scheduled-only (`service.py:891-892`). Recall (`POST /campaigns/{id}/recall`, `router.py:196`) needs `push.send` and works only on a sent announcement (`service.py:899-913`). Editing a sent campaign is `409 campaign-not-editable` (`service.py:806-807`). Stats and recipients endpoints (`router.py:208,213`) are not described.
- [undocumented] Campaign content checks: links must be https, and push bodies are at most 180 characters (`service.py:760-772`; DB checks `models.py:215,262`). Email fan-out skips a second recipient with the same address as `duplicate` (`service.py:962-966`).
- [undocumented] An announcement (push channel) writes an inbox item for every audience member with no `is_subscribed` check (`service.py:943-951`). Only the device sends are gated (`service.py:957-961`, `_deliver` push branch `:438-440`). README:53-54 states the check only for push automations.
- [undocumented] Templates have a third origin, `preset`, which is read-only (`409 template-read-only`, `service.py:546-547`; `models.py:205-232`). Deleting a template that campaigns, rules or messages use retires it (`is_active=false`) instead of deleting (`service.py:560-577`). Deleting a segment a campaign uses is `409 segment-in-use` (`service.py:704-705`). None is in README:60-62.
- [undocumented] Portal settings behaviour: settings start disabled and non-public, and the slug is generated from the location name (`service.py:1707-1722`). A slug already used is `409 portal-slug-taken` (`service.py:1741-1746`). Changing `terms_text` bumps `terms_version` (`service.py:1735-1737`), and `GET /public/portal-config` returns terms text and version (`service.py:1757-1758`). README:3-5 and README:135 mention portal settings only in passing; the terms and slug rules are unrecorded.
- [undocumented] Staff preference routes `GET|PUT /clients/{client_id}/communication-preferences` (`router.py:37-48`, `service.py:193-206`) are not in README. A staff change requires a `note` (`service.py:201-202`) and accepts a `basis` from `express`, `express_written`, `express_verbal`, `implied_purchase` or `implied_inquiry` (`schemas.py:42`). The README mentions only the portal route (README:125).
- [undocumented] `automation_rule.is_system` guards exist (`models.py:476`; `service.py:1546-1549,1560-1561`: a built-in rule can be switched off, not deleted), but nothing creates a system rule. README:100-101 says only that there is no built-in waitlist rule.
- [undocumented] The automation trigger catalogue (`service.TRIGGERS`, `service.py:1487-1494`: six events, README:67 names none) and two handlers README:12 does not name: reminders move on `scheduling.booking.rescheduled` (`handlers.py:34-36`), and `memberships.contract.renewed` is a trigger (`handlers.py:88-91`). An enrollment or waitlist promotion without a `session_id` skips reminders and alerts (`handlers.py:44-47,70-71`).
- [undocumented] README:16 lists four web screen groups. `web/src/features/engagement/` also holds `UnsubscribePage.tsx` (the public preference-centre page), `MessagesPages.tsx` (the delivery log) and `PortalPage.tsx` (portal settings).
- [wording] README:43-45 says an opt-in "needs an express basis (`express_written` or `express_verbal`)". Plain `express` is also accepted and is the default (`schemas.py:42`; `service.py:115`), and `import_consent` records `express` in GDPR mode (`service.py:176`). Only the `IMPLIED` set (`service.py:56`) is refused.
- [wording] README:11 and README:20 call `_deliver` the one send path for every email. Two things skip it: the `duplicate` skip row in `_fan_out` is built directly (`service.py:962-966`), and announcements and push automations write `InboxItem` rows directly with no `message` row (`service.py:943-951,1451-1458`). No email is sent outside it.
- [wording] The `POST /portal/devices` docstring says "Re-registering the same token moves it to this login" (`router.py:422-423`). The code revokes the other login's row and adds a new one (`service.py:1296-1303`), as README:96-98 says. The code comment is the stale side.
