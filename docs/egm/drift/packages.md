Recent change (`_credit_back`, `_live_charge`, `_clear_stale_failures`): edge cases the README does not state

- [resolved] Discount cap: the README says the discount is kept flat (not pro rata) and capped at the new gross, and `int(min(charge.discount_minor, left * charge.unit_price_minor))` (`postbilled.py:421`) matches, with the int cast the README mentions (`:412`).
- [drift] `_live_charge` picks the newest live charge by `max(c.id)` (`postbilled.py:396`). That relies on ids ordering by creation (UUIDv7). If a line has several live charges (the code allows it) only the newest is adjusted and the others are left untouched. README says "the live charge" in the singular.
- [drift] `_live_charge` excludes only `reversal` kind and non-`active` status (`:391-395`). A staff edit of price or discount that is still live is followed from its current values and not flagged; only a quantity below the line's still-billed usage rows (`:414-418`) or no live charge (`:429`) sets `charge_changed_by_hand` (`:430`). The README names a reversal and removed sessions as "by hand", not a price edit, and the audit does not record that a replacement was used.
- [drift] `post_billed_line.charge_id` is rewritten to the replacement only on an adjust (`:422`). On a reverse (`:426`), or when no live charge is left, `charge_id` and `invoice_id` keep pointing at the old charge. `_live_charge` finds charges by source, not by `charge_id`, so a line whose `charge_id` was never set still gets its charge adjusted. Not documented.
- [drift] The hand-removed rule is `to_credit = max(0, len(rows) - max(0, still_billed - quantity))` (`:415-418`), with `still_billed` the usage rows of the line with `credited_at` null. It treats every session missing from the charge as removed by hand, including a quantity staff lowered for another reason. The README states the intent but not this inference.
- [drift] Credit-back writes no line and no totals: `post_billed_line.total_minor`, `session_count` and the old close's `total_minor` are unchanged; the only trace is the audit record `credited_sessions` on the line (`:430-431`). README says only that the charge is adjusted.
- [resolved] `_clear_stale_failures` touches only closes with `closing_on <=` this run's, counts a package as handled only when this run gave it a step that did not fail (`:337`), and audits each edited close (`cleared_failures`, `by_close`, `:350-352`). README lines 89-90 say the same.
- [resolved] `retry_close` locks packages through `_plan` before refreshing the close `FOR UPDATE` (`:364-366`) and filters lines to the current failures (`:367-368`). README line 92 says so.
- [undocumented] `_clear_stale_failures` runs in a retry too (`:375`) and takes `FOR UPDATE` on every other close of the location with failures and `closing_on` up to this one, in `id` order (`:347`), after the package locks. Concurrent closes or retries of one location contend on those rows. It does not touch the other close's totals. Not in the README.
- [undocumented] A repeat `POST /post-billed-closes` for an existing date returns before `_plan` and never clears stale failures (`:277-278`); only a new close or a retry does.

Post-billed behaviour not (or wrongly) described in the README

- [drift] The close and the preview disagree about credit-backs. `_plan` builds a line for a package with only a restored credit and no new usage with `rate = None` and `skipped_reason = "no-usage"` (`:216`, `:225`). The preview shows total 0, yet a real close acts on it (`_run` adds the credit step when `line["credits"]`, `:314-315`). The `preview_close` docstring admits "credit-backs are not shown" (`:257`); the README still says the preview "shows the same lines without writing".
- [drift] Failure codes are not listed. `_run` now also catches any other exception per step (savepoint rolled back, logged, code `unexpected-error`, `postbilled.py:324-326`), so the old "aborts the whole close" drift is resolved and the README says so. Left: `code` is the `DomainError` code, the literal `conflict` for an `IntegrityError` (`:323`) or `unexpected-error`, and the README names only the last. When a package fails in both steps `setdefault` keeps only the first code (`:323`, `:326`), so the second failure is invisible.
- [drift] Retry edge cases. `retry_close` re-plans only the failed ids (`:364-365`); a failed package with nothing owed or restored is not in the plan, so it drops out of `failures` with nothing done (`:374`). Retry bills usage only up to the original `closing_on`, and the new line belongs to the old close, whose `package_count`, `session_count` and `total_minor` grow (`:376-378`). A package that already has a line at this close gets only its credit-back re-run (`:369-373`). A retry publishes no event, so `packages.post_billed.period_closed` is not sent for its added lines. Retry on a close with no failures returns it unchanged (`:362-363`). If another close clears some failures between the unlocked read (`:358`) and the refresh (`:366`), the retry follows the refreshed list (`:367-368`) and runs nothing when it is empty; the README gives the lock order but not this.
- [drift] "Ended packages with nothing owed are neither read nor locked" is looser in code. `unbilled` counts any unbilled consumed usage regardless of date (`:187-193`), so an ended package whose only usage is dated after `closing_on` is selected and locked `FOR UPDATE` (`:207`), then dropped by the later filter (`:211`). The README test "nothing owed" means owed at any date, not at this close. The `test_a_close_reads_only_packages_with_something_owed` test does not cover that case.
- [drift] A package without auto-renew is ended by moving the end of `valid_during` to `max(lower, closing_on) + 1 day` and calling `service._expire` (`:466-470`); the window rewrite, audit and `PackageExpired` event are not described. The README rule "nothing is held and nothing was used after the closing date" is implemented as "no reserved credits and no unbilled usage of any date" (`:466`, `_usage(..., date.max, ...)`). It runs only inside `_bill`, so a package with no new usage at this close, or whose bill step failed, is never ended at that close.
- [drift] `_plan` picks up a package when it is active or has unbilled usage or a pending credit-back, whatever its status (`:201-204`). `unsettled_count` is the package-wide `sessions_reserved_count`, not only holds on or before `closing_on` (`:222`). The README does not mention the preview field or this scope.
- [wording] The router docstring and summary still say "Every open post-billed package at the location" (`router.py:282`); the code also covers ended or removed packages with usage or a pending credit-back.
- [undocumented] No invoice is created when the charge total is 0 (`:450`), so `invoice_id` stays null. README says each package gets "one `create_invoice_for_charges`".
- [undocumented] A usage row is reused when a credited source is used again: one `post_billed_usage` row per source, repointed to the new line with `credited_at` cleared (`:455-464`, unique key `uq_post_billed_usage`). The earlier line's link on that row is overwritten.
