- [contract] README 75 (`provider-not-configured`), 189-191 (`409 already-exists`); `schemas.py:117-127`, `service.py:678`, `models.py:138-140`. `createExternalConnection` lists `connection-exists` and `provider-not-available` (6753). The code accepts `default_income_account`, `sync_from` and `auto_sync` (plus the analytics keys). It has no sync mode, and `sync_from` is not validated.
- [contract] README 173-182; `schemas.py:170-175, 196-200`, `quickbooks.py:316-363, 437`. `runSync` (6928) answers the `Accepted` handle (7937) `{job_id, status: queued|running|succeeded|failed, resource_url}` and takes `SyncRun` with `local_kinds` (9341-9348). - [contract] README 179-180 (`GET .../sync`, `.../sync/reset`); `router.py:210-221`, `schemas.py:202-211`. `getSyncStatus` (6951) and `resetSync` (6969) answer `200` with no schema, and neither has a `security` line. `SyncStatusOut` (`idle|running|completed|failed`, `counts`, `next_on`, `last_on`, `retries_failed`, `beat_at`, `is_stale`) is not in the contract.
- [contract] README 180-182 (`options_unavailable`); `quickbooks.py:270-287`, `schemas.py:163-168`. `getSyncMappings` still lists `provider-unavailable` (6864), which the code no longer raises. `SyncMappings` (9308-9321) has no `options_unavailable`, and `SyncMapping` has an `id` and names a `sync_mapping` table (9298-9307) that the README (168-169) says is not built.

- [undocumented] README 93-94 (posting keys unique across kinds); `domain/journal.py:18-23`, `service.py:843`. - [undocumented] README 176-177 ("due tokens are refreshed under a row lock"); `quickbooks.py:83-97, 106`. `credentials()` locks and reloads the row on every call, not only when a refresh is due, so mapping reads and every posting hold the lock. `refresh_if_due` and `get_mappings` (`:283`) catch bare `Exception`, which would also swallow a database error.
- [undocumented] README 78-79 (a POST callback because a mutating GET is not allowed); `quickbooks.py:83-97, 270-287`. `GET .../sync-mappings` can refresh and reseal credentials, so this GET writes to the row and locks it.
- [undocumented] README 173-176; `quickbooks.py:316-347, 404-441`. The README leaves out several `run_sync` rules: days already failed are skipped unless `retries_failed` (`:429`), today or later is `422`, a body `location_id` is ignored when the connection has its own, a non-active connection is `409`, and a connection disconnected mid-job ends the job `failed`.
- [undocumented] README 177-180 (stale takeover); `quickbooks.py:346, 367-374, 399, 404-449`, `jobs.py:34-36`. A sync has no job id, so after a takeover a slow first chain and the new chain share one cursor, and the old chain's dead-letter `fail_sync` fails the new job. A job stored before `beat_at` existed is stale at once. A takeover is audited only as `integrations.sync.start`. The README also omits the `integrations.sync.reset` audit action, the `idle` status, and the fact that `GET .../sync` is gated by `integrations.sync.run` (`router.py:210-214`).
- [undocumented] README 190-191 (a pending or errored row is taken over); `service.py:670-701`, `quickbooks.py:165-172`. A takeover replaces `settings` (mappings, maps, sync cursor), credentials and starter, and it ends the earlier starter's link (`403 state-invalid`). It is audited as an ordinary `integrations.connection.create`. The README states only the takeover.
- [wording] README 70 (`FH-<LOCATION SLUG>-<YYYYMMDD>`); `service.py:813`. The slug is upper-cased and cut to 12 characters, so two locations that share a 12-character prefix get the same doc number for the same day.
