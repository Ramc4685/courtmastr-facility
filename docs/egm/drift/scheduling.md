- [contract] `POST /sessions/{schedule_session_id}/direct-link/regenerate` (`router.py:341`, `secret_response`) has no contract operation. Behaviour now matches "create or return" only in part: a first call returns the token once, a repeat call returns status with `token` and `path` null (`sharing.py:73-74`), and regenerate is the only way to get a new token. The contract has no response schema (only `default: Problem`) for any direct-link operation, so the nullable `token` and `path` of `DirectLinkOut` (`schemas.py:633-639`) are undocumented there. A replayed Idempotency-Key still gets 409, not the body (`secret_response`), and the contract does not say so. The path parameter is `schedule_session_id` in the code and `session_id` in the contract. README item 12 covers only the other `/sessions/{...}` routes.

- [undocumented] Several `sharing.py` behaviours are not in the README. `create_link` and regenerate refuse a cancelled session with `invalid-state-transition` (`sharing.py:70-71`). `resolve_link` also returns `spots_left`, `location_name` and `time_zone` (more than "minimal fields"), and requires `confirmed` status, so a tentative hold does not resolve (`sharing.py:94`). `add_participant` refuses a cancelled booking and a block, and `mark_attendance` on a cancelled booking is refused, both with `invalid-state-transition`. `remove_participant` refuses the organiser with the same code. The 409 for a booking without an organiser is not named. The organiser's row is audited and published as `participant.added` when first listed, under the `enrollment.create` key.
- [undocumented] Permission keys used by sharing are not named in the README, which says only "Gates reuse the enrolment and attendance keys". The participant routes use `enrollment.create`, `enrollment.cancel`, `attendance.mark` and `mark_exception` for a no-show. The direct-link routes (create, regenerate, revoke) use `registration_link.create` (`permissions.py:39`), so regenerate and revoke share the create key with no separate gate. Type grants use the tenant-scoped `scheduling.reservation_type.grant` (`permissions.py:41`).
- [undocumented] The erasure precheck (`subject.py:37-46`) blocks on a non-cancelled booking ahead where the client is the booking's client or a `BookingParticipant`. The README covers the block. Not covered: the code is `upcoming-booking` with one generic detail ("The client still has a booking ahead."), so staff cannot tell an own booking from a shared one. It also counts a participant row on a booking whose organiser is someone else, and the README gives no way to remove a participant on behalf of an erasure (`remove_participant` needs `enrollment.cancel` and refuses the organiser). If the erased client is the organiser, the participants stay on a booking the precheck already blocked.
- [undocumented] `_export` (`subject.py:25-34`) adds `shared_bookings` with `booking_id` and `attendance` per participant row. The README does not say the subject export includes shared bookings, nor that erasure leaves participant rows untouched while `_erase` clears notes only on the client's own bookings.
- [wording] The README says merge "Needs `update_series` on both bookings". The code checks the target via `_own` and the other via `_authorize` (`service.py:2184-2190`). A caller whose location scope excludes the other booking gets a 422 "No booking has that number." first (`service.py:2185-2188`), so the second check never gives a 403 or 404 for scope.
- [wording] The README says merge refuses "blocks and cancelled bookings". The code raises `invalid-state-transition` only when this booking is a block or either is cancelled (`service.py:2193`). A block on the other side is caught earlier as `merge-mismatch` because `kind` differs. The `series-run-in-progress` check (`service.py:2197-2203`) comes after the locks and after the mismatch checks, so a mismatched pair reports `merge-mismatch` first. It looks only at series that exist before the merge and only at runs in `pending` or `running`, and reads the runs without locking them, so a run started between the check and the commit is not excluded. Source series runs are re-pointed to the target (`service.py:2238-2241`), which the README never mentions. The audit sentence omits the rows for the emptied source series (`merged_into`) and for the target series (`service.py:2255-2263`).
- [undocumented] New merge locking is described in the README ("both series rows by id, then every booking of the two series by id") but not these details. The other booking is found by `booking_number` before any lock, then the pair is re-checked against the ids and series ids read at lock time (`service.py:2175-2195`), and a change in between gives 409 `invalid-state-transition` ("The bookings changed while linking; try again."), a code and message the README does not name. A number that matches no booking skips series locks and fails later as 422. The README's last sentence ("Both bookings are locked in id order") repeats the lock-order sentence before it.
- [wording] README item 8 and the "Assumptions" numbering are unchanged. Buffers in 5-minute steps are enforced only by the API schema (`schemas.py:17`) and the model, and the items run 1-11, 15-18, 12-14.

- [contract] `platform/README.md:43` says scheduling refuses "while a confirmed booking is still to start". The code also refuses on a live tentative checkout hold (`status = tentative` and `expires_at > now`, `service.py:983-985`), covered by `test_a_live_checkout_hold_blocks_archiving_until_it_expires`. Neither README describes the hold case, and a tentative booking with a null `expires_at` never blocks (the comparison is NULL).
- [undocumented] Archive-guard edges nobody documents. Blocks (`kind = block`, closures and staff time off) never refuse (`service.py:986-988`; test `test_a_future_closure_block_does_not_refuse_the_archive`). The boundary is `starts_at > now`, so a booking in progress or starting exactly now does not block. Only `booking` rows of that location count. Series occurrences not yet generated (a pending or running `generate` run), slot offers and availability windows are not checked, so a location with an offer or a series still generating can be archived and the worker then books at an inactive location. The check takes no lock and runs inside platform's archive transaction (`platform/service.py:272-273`), so a booking created between the check and the commit is not excluded.
- [contract] The guard's 409 body is a bare `Conflict` with a fixed sentence and no `extra` (no count or first booking), so staff cannot see which bookings to cancel. The contract documents only the code in `x-problem-codes`. The README does not say staff must cancel or move the bookings through the calendar first.
