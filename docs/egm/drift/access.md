## backend/app/modules/access/README.md

- [stale-not-built] README lines 142-144 say the card's `photo_url` "is always null until chip F adds `client.photo_file_id`". The code already wires it: backend/app/modules/access/desk.py:360 sets `photo_url` to `/api/v1/clients/{id}/photo` when the template has a photo slot and `client.photo_file_id` is set, and that route exists (backend/app/modules/clients/router.py:530).
- [contract] README line 11 gives `check_in.result` as `admitted` / `denied` / `see_staff`. The enum is `granted` / `denied` / `granted_override` (backend/app/modules/access/models.py:32-35, CHECK at :106). "See staff" is a kiosk response wording, not a stored result.
- [contract] README line 112 says "Check-ins are never deleted (no `deleteCheckIn`)", and the router has no delete route (backend/app/modules/access/router.py). Two things contradict this: the permission `access.checkin.delete` ("Delete a check-in and restore its visit") is still registered (backend/app/modules/access/permissions.py:20), and the contract still publishes `deleteCheckIn` (docs/api/openapi-money.yaml:4052).
- [contract] docs/api/openapi-money.yaml declares access paths the router lacks: `/kiosk/check-ins/{check_in_id}/attendances` (`createKioskAttendance`, :4383), `/check-ins/{check_in_id}/eligible-sessions` (~:4521), `/portal/app-cards/{credential_id}/wallet-pass` (~:4715) and `/kiosk/package-purchases` (`createKioskPackagePurchase`, :4731). None is in router.py, and the README does not mark them deferred, apart from the wallet pass (line 153). In the other direction, `GET /membership-type-access` (router.py:202-205) is not in the contract.
- [wording] README line 13 lists credential kinds as "barcode, RFID, PIN-free card numbers and app cards". The enum is `membership_number`, `barcode`, `app_card`, `wallet_pass`, `rfid`, `biometric_ref` (models.py:38-44). There is no "PIN-free card number" kind, and `wallet_pass` / `biometric_ref` are not mentioned.
- [wording] README lines 57-59 say the staff-window attendance window is "3 hours early to 5 hours late". `programs.service.mark_attended_by_check_in` marks sessions starting from `early` before to `late` after the check-in (backend/app/modules/programs/service.py:645-646). The staff path passes early=180 min and late=300 min (access/service.py:244-246, defaults :770-772; domain/evaluate.py:13-15). For the client, that means up to 3 h late and up to 5 h early. The kiosk path passes the settings swapped, `(late_window_minutes, early_window_minutes)` (service.py:727). So "early" means opposite things on the two paths, and the README's phrasing follows neither consistently.
- [wording] README lines 125-126 say configuration changes are audited without events and "only the access-mode change publishes one". README line 145 says station and card-layout changes publish events, which they do (events.py:35-45). The code also publishes `access.credential.assigned` (events.py:48-50).
- [undocumented] The README never mentions the check-in lifecycle events `access.check_in.granted`, `access.check_in.denied`, `access.check_in.checked_out` and `access.check_in.session_booked` (backend/app/modules/access/events.py:16-30). Line 96 says only "published per row".
- [undocumented] The permissions `access.door.unlock` and `access.device.manage` (permissions.py:28-29) are registered with no route. The README's deferred hardware note (line 152) does not mention them.
- [undocumented] Check-in channels include `pos`, `door` and `api` (models.py:17-23) and `identified_by` has `client_record` (models.py:26-29). README lines 3-5 name only the staff window, client profile, kiosk and app-card paths.
- [undocumented] Erasure also drops the client's access mode (backend/app/modules/access/subject.py:4, tables at :65). README lines 105-107 mention only revoked credentials, kept check-ins and dropped match tokens.
- [undocumented] `GET /check-ins` also filters by `check_in_station_id` (service.py:359-362). The router docstring and README line 136 list only the other filters.
