## backend/app/modules/scheduling/README.md

- [contract] The sharing routes do not match `docs/api/openapi-core.yaml`, and the README does not say so. `POST /bookings/{booking_id}/merge` (`router.py:387`) takes a booking id and a `booking_number` body. The contract's `mergeBookingSeries` (`openapi-core.yaml:3383-3396`) is `POST /booking-series/{booking_series_id}/merge`. The four participant routes (`router.py:359-384`) are in no `docs/api/*.yaml`. The contract's out-of-scope note (`openapi-core.yaml:47`) still gives shared bookings (SCH-17) to packages ("share rows"). The code owns them in scheduling (`sharing.py`, `models.py` `BookingParticipant`).
- [contract] `resolveDirectLink` is `GET /public/direct-links/{token}` with the token in the path, recorded as an accepted exception to "no secrets in URLs" (`openapi-core.yaml:3337-3352`). The code serves `POST /public/direct-links/resolve` with the token in the body (`router.py:346`). The exception text is stale. The contract says it resolves "its session or slot offer", but `sharing.resolve_link` (`sharing.py:78-91`) queries `Session` only.
- [contract] The contract summary for `createSessionDirectLink` reads "Create or return the reusable direct registration link" (`openapi-core.yaml:3300`). The code never returns an existing link. Only a sha256 digest is stored (`sharing.py:64`), so every POST issues a new token and replaces the old one, and the token is returned once via `@secret_response` (`router.py:329-330`). A replayed Idempotency-Key gets 409, not the body. The contract documents neither, and has no response schema (only `default: Problem`) for either direct-link operation. The code returns `DirectLinkOut` (`schemas.py:633`) and 204. The path parameter is `schedule_session_id` in the code and `session_id` in the contract. README item 12 covers only the other `/sessions/{...}` routes.
- [contract] `createSlotOfferDirectLink` (`openapi-core.yaml:3322`) has no route. The README "Not built" list says "direct links for slot offers" without naming the operation. `slot_offer.direct_link_token` is still generated as a raw token (`offers.py:157`, `models.py:541`) and never read, so it sits in the same shape the session column had before digesting. Whoever builds the slot-offer link must digest it too.
- [contract] Still open from earlier. `PATCH /booking-series/{id}/rules/{rule_id}` (`router.py:247`) and `GET` and `POST /slot-offers/{slot_offer_id}/slots` (`router.py:318,324`) have no contract operation. `getPublicSchedule`, `getPublicScheduleSettings` and `updatePublicScheduleSettings` (`openapi-core.yaml:3356-3375`, SCH-20) have no route, and the last two are named nowhere in the README. `scheduling.public_schedule.manage` is registered (`permissions.py:42`) with no route.
- [contract] The `series-run-in-progress` 409 is documented only in the README. The merge router docstring (`router.py:389-392`) lists `already-linked` and `merge-mismatch` but not `series-run-in-progress` or `invalid-state-transition`. The contract's `mergeBookingSeries` lists no error codes.

- [stale] The `sharing.py` module docstring (`sharing.py:3-6`) says a session's `direct_link_token` "exists from creation" and "revoking rotates the token". Since the digest change, the column holds a digest after the first POST and a throwaway digest after revoke. Before the first POST it holds a raw random value set at `service.py:658` (`secrets.token_urlsafe(16)`) that nobody was ever given and that cannot match `digest(token)`. The column name `direct_link_token` (`models.py:497`) is therefore misleading, and no doc says it holds a digest.
- [undocumented] The README does not say that revoke replaces the digest with a fresh random digest. It also does not say that audit records `is_direct_link_active` and `token_rotated` and never the token (`sharing.py:49`). The `programs` caller `selfservice.py:205` passes the raw token through `has_live_link`.
- [undocumented] The "Interface for other contexts" block (README lines 19-30) omits `service.has_live_link(session, session_id, token) -> bool` (`service.py:843`). - [undocumented] Several `sharing.py` behaviours are not in the README. `create_link` refuses a cancelled session with `invalid-state-transition` (`sharing.py:61-62`). `resolve_link` also returns `spots_left`, `location_name` and `time_zone` (more than "minimal fields"), and requires `confirmed` status, so a tentative hold does not resolve (`sharing.py:83`). `add_participant` refuses a cancelled booking and a block, and `mark_attendance` on a cancelled booking is refused, both with `invalid-state-transition`. `remove_participant` refuses the organiser with the same code. The 409 for a booking without an organiser (`invalid-state-transition`) is not named. The organiser's row is audited and published as `participant.added` when first listed, under the `enrollment.create` key.
- [undocumented] Permission keys used by sharing are not named in the README, which says only "Gates reuse the enrolment and attendance keys". The participant routes use `enrollment.create`, `enrollment.cancel`, `attendance.mark` and `mark_exception` for a no-show. The registration link uses `registration_link.create` (`permissions.py:39`). Type grants use the tenant-scoped `scheduling.reservation_type.grant` (`permissions.py:41`).
- [undocumented] The erasure precheck (`subject.py:37-46`) blocks on a non-cancelled booking ahead where the client is either the booking's client or a `BookingParticipant`. This is in the README ("waits while they are a participant on a booking ahead"). Not in the README: the precheck code is `upcoming-booking` with a single generic detail ("The client still has a booking ahead."), so staff cannot tell from the response whether the block is an own or a shared booking. It also counts a participant row on a booking whose organiser is someone else, which staff must cancel or reassign, but the README gives no way to remove a participant on behalf of an erasure (`remove_participant` needs `enrollment.cancel` and refuses the organiser). If the erased client is the organiser, the participants stay on a booking the precheck already blocked.
- [undocumented] `_export` (`subject.py:25-34`) adds `shared_bookings` with `booking_id` and `attendance` per participant row. The README does not mention that the subject export includes shared bookings, nor that erasure leaves participant rows untouched while `_erase` clears notes only on the client's own bookings.
- [wording] The README says merge "Needs `update_series` on both bookings". The code checks the target via `_own` and the other via `_authorize` (`service.py:2157-2165`). A caller whose location scope excludes the other booking gets a 422 "No booking has that number." first (`service.py:2159-2162`), so the second check never gives a 403 or 404 for scope.
- [wording] The README says merge refuses "blocks and cancelled bookings". The code raises `invalid-state-transition` only when this booking is a block or either is cancelled (`service.py:2170`). A block on the other side is caught earlier as `merge-mismatch` because `kind` differs. The `series-run-in-progress` check (`service.py:2172-2178`) looks only at series that exist before the merge and only at runs in `pending` or `running`. It runs after the row locks are taken and after the mismatch checks, so a mismatched pair reports `merge-mismatch` first. The check also reads runs without locking them, so a run started between the check and the commit is not excluded. Source series runs are re-pointed to the target (`service.py:2213-2216`), a step the README never mentions. The audit sentence omits the audit rows for the emptied source series (`merged_into`) and for the target series (`service.py:2225-2234`).
- [wording] README item 8 and the "Assumptions" numbering are unchanged. Buffers in 5-minute steps are enforced only by the API schema (`schemas.py:17`) and the model, and the items run 1-11, 15-18, 12-14.
- [undocumented] Location-archive guard (main). `service.check_location_archive` (`service.py:974-987`) is registered with platform at import time (`__init__.py:10-12`, `platform.service.register_location_archive_check`) and refuses `POST /locations/{id}/archive` with 409 `location-has-future-bookings`. The scheduling README never mentions it: not in the "Interface for other contexts" block (README lines 19-30), the file table, the "Calls `platform`, `resources`, `clients`" line (the guard is a callback into `platform`, and `__init__.py` imports `platform`, which the intro does not say), or "Assumptions". Only `platform/README.md:43` and the contract's `archiveLocation` `x-problem-codes` (`openapi-core.yaml:696`) name it. Evidence of behaviour is `tests/test_location_archive.py`.
- [contract] `platform/README.md:43` says scheduling refuses "while a confirmed booking is still to start". The code also refuses on a live tentative checkout hold (`status = tentative` and `expires_at > now`, `service.py:978-981`), which the test `test_a_live_checkout_hold_blocks_archiving_until_it_expires` covers. Neither README describes the hold case, and a tentative booking with a null `expires_at` never blocks (the comparison is NULL).
- [undocumented] Archive-guard edges nobody documents. Blocks (`kind = block`, closures and staff time off) never refuse (`service.py:982-983`). The test is `test_a_future_closure_block_does_not_refuse_the_archive`. The boundary is `starts_at > now`, so a booking in progress or starting exactly now does not block. The guard counts only `booking` rows of that location. Series occurrences not yet generated (a pending or running `booking_series_run` of kind `generate`), slot offers and availability windows are not checked, so a location with an offer or a series still being generated can be archived and the worker then books at an inactive location. The check takes no lock and runs inside platform's archive transaction (`platform/service.py:272-273`), so a booking created between the check and the commit is not excluded.
- [contract] The guard's 409 body is a bare `Conflict` with a fixed sentence and no `extra` (no count or first booking), so staff cannot see which bookings to cancel. The contract documents only the code in `x-problem-codes`, with the generic `Conflict` response and no body schema. The README does not say staff must cancel or move the bookings through the calendar first.
