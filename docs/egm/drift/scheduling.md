## backend/app/modules/scheduling/README.md

- [contract] The three new sharing routes of the Phase 14 C2 section have no operation in the contract, and the two that do exist differ in shape. `POST /bookings/{booking_id}/merge` (`router.py:387`) takes a booking id and a `booking_number` body, but `openapi-core.yaml:3383-3396` defines `mergeBookingSeries` as `POST /booking-series/{booking_series_id}/merge` on a series id. The participant routes, `GET` and `POST /bookings/{booking_id}/participants` and `PATCH` and `DELETE .../participants/{participant_id}` (`router.py:359-384`), appear in no `docs/api/*.yaml`. `openapi-core.yaml:47-48` says shared bookings (SCH-17) belong to packages ("share rows"), but the code owns them in scheduling (`sharing.py`, `models.py:376`). The README (lines 109-127) does not mention either gap.
- [contract] `resolveDirectLink` is `GET /public/direct-links/{token}` with the token in the path (`openapi-core.yaml:3335-3352`, which records it as an accepted exception to "no secrets in URLs"). The code serves `POST /public/direct-links/resolve` with the token in the body (`router.py:346`, `sharing.py:resolve_link`). The README documents the code's version (line 112) and never says the contract says otherwise. The contract's exception text and the "redacted from logs" note are now stale.
- [contract] `createSessionDirectLink` and `revokeSessionDirectLink` are built (`router.py:333,339`), but the README "Not built" list (lines 104-107) still says "direct links for slot offers" without naming `createSlotOfferDirectLink` (`openapi-core.yaml:3321`). There is no route for it, although `slot_offer.direct_link_token` is generated on create (`offers.py:157`; `models.py:541`) and never read. The contract also says `createSessionDirectLink` serves SCH-17 (`openapi-core.yaml:3300`), which the code does through the participant routes instead.
- [contract] The contract's `resolveDirectLink` is described as resolving "its session or slot offer". The code resolves sessions only (`sharing.py:resolve_link` queries `Session` only). The README states one link per session (line 114) but does not call out the slot-offer gap.
- [contract] The contract's `createSessionDirectLink` and `revokeSessionDirectLink` have no response schemas (only `default: Problem`). The code returns `DirectLinkOut` for create (`session_id`, `is_active`, `token`, `path`) and 204 for revoke (`router.py:333,339`). The path parameter is also `schedule_session_id` in the code, `session_id` in the contract (README item 12 covers only the `/sessions/{...}` routes of that name).
- [contract] Still true from the earlier report: `PATCH /booking-series/{id}/rules/{rule_id}` (`router.py:247`) and `GET` and `POST /slot-offers/{slot_offer_id}/slots` (`router.py:318,324`) have no operation in the contract. `getPublicSchedule`, `getPublicScheduleSettings` and `updatePublicScheduleSettings` (SCH-20) still have no route, and `getPublicScheduleSettings` and `updatePublicScheduleSettings` are named nowhere in the README. `scheduling.public_schedule.manage` is registered (`permissions.py:42`) with no route.

The file table (lines 7-16) lists neither `sharing.py` nor `subject.py`, `events.py` or `permissions.py`, and `models.py` omits `booking_participant` (`models.py:376`).

- [undocumented] Four behaviours of `sharing.py` are not in the README. A `mark_attendance` call for a cancelled booking is refused with `invalid-state-transition` (`sharing.py:mark_attendance`). `add_participant` also refuses a cancelled booking and a block. `resolve_link` returns `spots_left`, `location_name` and `time_zone`, not only "minimal fields" (`sharing.py:resolve_link`). `resolve_link` also requires the booking to be `confirmed`, not only not cancelled, so a tentative hold does not resolve. `create_link` refuses a cancelled session with `invalid-state-transition`.
- [undocumented] The new permissions used by sharing are not tied to the README. The participant routes reuse `enrollment.create`, `enrollment.cancel` and `attendance.mark` (`sharing.py:ENROLL`, `UNENROLL`, `MARK`), and the registration link uses `registration_link.create` (`permissions.py:40`), granted at `_FD` level and location scope. The README says only "Gates reuse the enrolment and attendance keys".
- [wording] The README says merge "needs `update_series` on both bookings" (line 125). The code checks it on the target through `_own` and on the other booking through `_authorize` (`service.py:2141-2146`), but a caller whose location scope excludes the other booking gets a 422 "No booking has that number." instead, so the second check cannot report a 403 or 404.
- [wording] The README says merge "blocks" and cancelled bookings are refused (line 126), but the code refuses with `invalid-state-transition` when this booking is a block or either is cancelled, and a block on the other side is caught earlier by the mismatch check (`kind` differs) as `merge-mismatch` (`service.py:2154-2156`). The error codes `already-linked`, `merge-mismatch` and `invalid-state-transition` are named only in the router docstring.
- [wording] README item 8 and the "Assumptions" numbering issues from the earlier report are unchanged: buffers in 5-minute steps are enforced only by the API schema (`schemas.py:17`, `models.py:117,128`), and items run 1-11, 15-18, 12-14 (lines 47-100). Type grants use the tenant-scoped key `scheduling.reservation_type.grant` (`permissions.py:41`), which the README never names.
