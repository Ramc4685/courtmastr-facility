## backend/app/modules/resources/README.md

- **Stale "staff does not exist yet" note (README lines 26-28).** The doc says the `staff` context and its `staff.trainer.created` event do not exist, and module 12 "should create them from that event instead". Both exist now: `backend/app/modules/staff/events.py:9-15` (`TrainerCreated`, type `staff.trainer.created`). Staff did not take the event-driven route the doc plans. `create_payee` calls `resources.service.create_resource(...)` directly (`backend/app/modules/staff/service.py:158-162`) and publishes `staff.trainer.created` only afterwards (`staff/service.py:174-177`). `POST /resources` with `kind: trainer` + `staff_user_id` still works too (`resources/service.py:152-165`), so there are now two ways to create a trainer.
- **Internal interface list is incomplete (README line 10).** `trainer_group(session, location_id)` (`backend/app/modules/resources/service.py:376-391`) is a cross-context function the README does not list. It creates a "Trainers" schedule group when the location has none, and staff calls it (`staff/service.py:158`). The line also says the interface is what "scheduling uses". Staff calls it as well: `get_many` at `staff/service.py:130`, `create_resource` at `staff/service.py:159`.
- **`counts_toward_plan` default is broader than documented (README line 20).** The doc names only sub-venues as defaulting to false. The code also defaults `virtual_room` to false (`resources/service.py:153-154`). The database column default is `true` (`resources/models.py:74`), so the rule lives only in `create_resource`.
- **League venue mapping is partly built, not "Not built" (README line 38, RES-06).** Leagues already put games on facility resources. The schedule wizard carries `resource_ids` (`backend/app/modules/leagues/models.py:404`), and a game has `resource_id` + `booking_id` with a check that a scheduled game has both (`leagues/models.py:428-458`), so games occupy the facility calendar. The missing part is a separate league venue list mapped to resources. `docs/planning/remaining-work.md:52-53` already notes that the docs disagree about RES-06.
- **Locker and padlock permission keys exist though the features are listed as not built (README line 37).** `resources.locker.manage`, `resources.padlock.manage` and `resources.padlock.reveal_combination` are registered (`resources/permissions.py:16-18`). They have no tables or routes (`resources/models.py:1`; `rentals/models.py:1-2`). The README does not mention that these keys are already in the catalogue.
- **"14 operations of tag `resources`" understates the contract (README line 11).** `docs/api/openapi-core.yaml` has 23 operations tagged `resources`. The router serves 14 (`resources/router.py:24-98`). The other 9 locker operations (`listLockerRooms`, `createLockerRoom`, `updateLockerRoom`, `listLockers`, `bulkCreateLockers`, `updateLocker`, `listLockerTerms`, `createLockerTerm`, `updateLockerTerm`) are not served, and the README does not say they exist in the contract.
- **Advice on a refused window delete conflicts with scheduling's docs (README lines 32-33).** The README says that when a slot is already taken, "the window should be paused". The refusal is a database rule: `session.slot_offer_id` is a RESTRICT FK, and `slot_offer` cascades from the window (`backend/migrations/versions/1001_scheduling_slot_offers_and_type_grants.py:57,82`). `backend/app/modules/scheduling/README.md:85-86` says to pause the *offer* instead. `delete_window` (`resources/service.py:303-309`) has no check of its own, so the README's wording points at the wrong place.
- **Staff screens are not mentioned.** `web/src/features/resources/ResourcesPage.tsx` (with `queries.ts` and a test) implements this module's UI. The README has no screens section or pointer to it.
