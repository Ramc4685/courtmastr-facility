## backend/app/modules/scheduling/README.md

- [contract] The sharing routes of the Phase 14 C2 section do not match the contract, and the README does not say so. `POST /bookings/{booking_id}/merge` (`router.py:387`) takes a booking id and a `booking_number` body. `openapi-core.yaml:3383-3396` defines `mergeBookingSeries` as `POST /booking-series/{booking_series_id}/merge` on a series id. `GET` and `POST /bookings/{booking_id}/participants` and `PATCH` and `DELETE .../participants/{participant_id}` (`router.py:359-384`) appear in no `docs/api/*.yaml`. The contract's out-of-scope note (`openapi-core.yaml:47`) still says shared bookings (SCH-17) belong to packages ("share rows"). The code owns them in scheduling (`sharing.py`, `models.py:376`).
- [contract] `resolveDirectLink` is `GET /public/direct-links/{token}` with the token in the path (`openapi-core.yaml:3337-3352`, recorded there as an accepted exception to "no secrets in URLs", "redacted from logs"). The code serves `POST /public/direct-links/resolve` with the token in the body (`router.py:346`, `sharing.py:resolve_link`). The README describes the code's version only, so the contract's exception text is stale. The contract says it resolves "its session or slot offer", but `resolve_link` queries `Session` only.
- [contract] `createSlotOfferDirectLink` (`openapi-core.yaml:3322`) has no route. `slot_offer.direct_link_token` is generated on create (`offers.py:157`, `models.py:541`) and never read. The README "Not built" list says only "direct links for slot offers" without naming the operation. The contract also ties `createSessionDirectLink` to SCH-16 and SCH-17 (`openapi-core.yaml:3300`), but the code serves SCH-17 through the participant routes.
- [contract] `createSessionDirectLink` and `revokeSessionDirectLink` have no response schemas in the contract (only `default: Problem`). The code returns `DirectLinkOut` (`session_id`, `is_active`, `token`, `path`) and 204 (`router.py:333,339`). The path parameter is `schedule_session_id` in the code and `session_id` in the contract. README item 12 covers only the other `/sessions/{...}` routes.
- [contract] Still open from earlier: `PATCH /booking-series/{id}/rules/{rule_id}` (`router.py:247`) and `GET` and `POST /slot-offers/{slot_offer_id}/slots` (`router.py:318,324`) have no operation in the contract. `getPublicSchedule`, `getPublicScheduleSettings` and `updatePublicScheduleSettings` (`openapi-core.yaml:3356-3375`, SCH-20) have no route, and the last two are named nowhere in the README. `scheduling.public_schedule.manage` is registered (`permissions.py:42`) with no route.
- [stale] README line 15 reads "31 operations of `openapi-core.yaml` tag `scheduling`, plus 8 from phase 10". `router.py` declares 48 route decorators (47 on `router`, 1 on `public`). Eight came with Phase 14 C2 (two direct-link, one resolve, four participant, one merge) and are not counted. The file table (lines 7-16) lists no `sharing.py`, `subject.py`, `events.py` or `permissions.py`, and the `models.py` row omits `booking_participant` (`models.py:376`).
- [undocumented] The README does not list the events `scheduling.session.direct_link_changed`, `scheduling.participant.added`, `.removed` and `.attendance_marked`, and `scheduling.series.merged` (`events.py:86-126`). Line 89 says only "the usual events". The earlier booking, session, series, slot offer and grant events are also unlisted.
- [undocumented] The "Interface for other contexts" block (README lines 19-30) omits `service.has_live_link(session, session_id, token)` (`service.py:842`). The README mentions it only in the direct-link bullet (line 115), with no signature and no `None`/empty-token behaviour (returns False). The block also omits `merge_series` (`service.py:2145`, router-facing, takes a principal) and these older internal functions: `booking_views`, `booking_ids`, `hold_plan`, `book`, `free_ranges` (`service.py:396,916,923,1147,2087`), plus `sessions_with_resource`, `series_sessions`, `type_location`, `session_window`, `series_scope`, `template_for`, `hours_warnings` and `client_bookings_starting`.
- [undocumented] Several `sharing.py` behaviours are not in the README. `add_participant` also refuses a cancelled booking and a block with `invalid-state-transition`. `mark_attendance` on a cancelled booking is refused with `invalid-state-transition`, and `remove_participant` refuses the organiser with the same code. `add_participant` allows the organiser as the added client. `resolve_link` also returns `spots_left`, `location_name` and `time_zone` (more than "minimal fields"), and requires `confirmed` status, so a tentative hold does not resolve. `create_link` refuses a cancelled session with `invalid-state-transition`. The README gives the 409 for a booking without an organiser but not its code (`invalid-state-transition`, `sharing.py:166-171`). It also does not say that the organiser's row is audited and published as `participant.added` when first listed (`sharing.py:177-185`), under the `enrollment.create` key.
- [undocumented] Permission keys used by sharing are not tied to the README. The participant routes reuse `enrollment.create`, `enrollment.cancel` and `attendance.mark` (`sharing.py:30` and `MARK`), plus `mark_exception` for a no-show. The registration link uses `registration_link.create` (`permissions.py:39`, `_FD`, location scope). The README says only "Gates reuse the enrolment and attendance keys". Type grants use the tenant-scoped `scheduling.reservation_type.grant` (`permissions.py:41`), which the README never names.
- [wording] The README says merge "Needs `update_series` on both bookings". The code checks it on the target through `_own` and on the other through `_authorize` (`service.py:2155-2159`). A caller whose location scope excludes the other booking gets a 422 "No booking has that number." first (`service.py:2152-2154`), so the second check never reports a 403 or 404 for scope.
- [wording] The README says merge refuses "blocks and cancelled bookings". The code refuses with `invalid-state-transition` only when this booking is a block or either one is cancelled (`service.py:2167`). A block on the other side is caught earlier as `merge-mismatch` because `kind` differs. The codes `already-linked`, `merge-mismatch` and `invalid-state-transition` are named only in the router docstring. The README's audit sentence also omits that the emptied source series and the target series get their own audit rows (`service.py:2217-2229`).
- [wording] README item 8 and the "Assumptions" numbering issue are unchanged. Buffers in 5-minute steps are enforced only by the API schema (`schemas.py:17`, `models.py:117,128`), and the items run 1-11, 15-18, 12-14.
