## backend/app/modules/integrations/README.md

Fresh report, 2026-11-13, on `claude/phase15-public-api-integrations` (working tree, including the uncommitted INT-07 QuickBooks work: `quickbooks.py`, `router.py`, `schemas.py`, `service.py`, `ports/accounting.py`, `adapters/accounting.py`). Read-only, no tests run. Paths are under `backend/app/modules/integrations/` unless they start with `docs/`, `config/`, `web/` or `backend/`. README line numbers are the working-tree README (113 lines). Contract line numbers are `docs/api/openapi-programs.yaml`. The README gained the QuickBooks rows and rules since the last report, so its line numbers moved.

Resolved by the builder right after this report, before commit (tested): the `status_url` 404 (now the flat `GET /accounting-exports?external_connection_id=`), `connected_at` on a pending connection, the cross-kind posting-key collision, the webhook trusting the simulated adapter's public secret (401 while QuickBooks is off and outside dev and test), and the stale docstrings. The README now lists the remaining unbuilt ADR 0012 rules, the unused `sync_from`/`auto_sync`, and the insert-only realm lookup. Line numbers below predate those edits.

### INT-07 QuickBooks Online (new)

- [contract] Deliberate deviation, already written down in the README (lines 62-69). `completeExternalConnectionOAuth` is `GET` with `state`, `code`, `realm_id`, `error` in the query and answers `302` (openapi-programs.yaml:6745-6770). The code serves `POST /external-connections/oauth/callback` with a JSON body and answers `200 {external_connection_id, status, return_url}` (`router.py:157-166`, `schemas.py:165-175`), following the OIDC callback and the no-mutating-GET rule (`quickbooks.py:58-61`). The yaml was not updated. Also the yaml types `realm_id` as `format: uuid`, but a QuickBooks realm is a numeric string and the code takes a plain string (`schemas.py:168`, FakeQuickBooks uses `9130000000000001`, `adapters/accounting.py:102`).
- [contract] Path parameter is `connection_id` in the contract for every `/external-connections/{connection_id}...` operation (openapi-programs.yaml:6771, 6811, 6834, 6875, 6912) and `external_connection_id` in the code (`router.py:169-222`). Same URL on the wire, different parameter name in the generated spec and in `web/src/api/schema.d.ts`.
- [contract] `ExternalConnection` response shape. The contract returns `granted_scopes`, `settings` and `updated_at`, and `authorize_url` "while pending" (openapi-programs.yaml:9085-9107). `ExternalConnectionOut` has none of the first three (`schemas.py:118-128`) and `authorize_url` exists only on the create response (`schemas.py:131-132`, `router.py:154`). So `getExternalConnection` cannot return the link of a pending connection, and `PATCH` settings can never be read back; `return_url`, `mappings`, `account_map` and `class_map` also live in that same `settings` blob (`quickbooks.py:101, 248`).
- [contract] `createExternalConnection`. The contract documents `409 connection-exists` and `422 provider-not-available` (openapi-programs.yaml:6742-6743). Code: `provider` is a two-value `Literal` (`schemas.py:110`), so any other provider is a generic validation 422; a QuickBooks create with the flag off is `422 provider-not-configured` (`service.py:653-656`), which the contract does not list; a duplicate (provider, location) hits `uq_external_connection` (`models.py:137-139`) and returns the generic `409 already-exists` (`core/api.py:321-322`, no `CONSTRAINT_CODES` entry). `ExternalConnectionCreate` also accepts `settings` (`schemas.py:112-114`), which the contract schema (openapi-programs.yaml:9109-9116) lacks.
- [contract] `updateExternalConnection`. The contract says settings are "sync_from date, sync mode (invoice or daily summary), auto-sync flag" and the body is `application/merge-patch+json` (openapi-programs.yaml:6803, 9123-9124). The code accepts `default_income_account`, `sync_from`, `auto_sync` (`quickbooks.py:37`); there is no sync mode. `sync_from` is an unvalidated string (`schemas.py:136`).
- [missing] `sync_from` and `auto_sync` are stored but nothing reads them. The export reads only `account_map`, `class_map` and `default_income_account` (`service.py:775-778`), and no job or event pushes automatically. The README does not call them stored-only.
- [contract] `runSync` is documented as a job that "creates or retries the accounting_export row of each location and day in the range" and answers an `Accepted` handle (openapi-programs.yaml:6919-6940). The code runs in the request (README line 107 says so) for one location only (the connection's, or the `location_id` the body names, `quickbooks.py:268-270`), returns `{status: "completed", counts, status_url}` (`schemas.py:182-185`), takes `location_id` which the contract's `SyncRun` lacks, and has no `local_kinds` (`schemas.py:158-162`, contract openapi-programs.yaml:9170-9176). `mappings-incomplete` (422) is never raised: an unmapped QuickBooks key fails that day's export with a plain validation message instead (`service.py:785-786`), a revenue key with a default income account posts with a warning (:781-784).
- [contract] `status_url` in the sync response is `/api/v1/external-connections/{id}/accounting-exports?location_id=...` (`quickbooks.py:292`), the contract's nested path. The router does not serve it; it serves the flat `GET /accounting-exports` (`router.py:229`). The returned link would 404.
- [contract] `listAccountingExports` is still not served at its contract path (openapi-programs.yaml:6875), and the flat route that is served lacks the `business_on[gte]`, `business_on[lte]` filters and the `status[in]` form (`service.py:812-815`, filter fields `external_connection_id`, `location_id`, `status`).
- [contract] `AccountingExport` response. The contract has `supersedes_export_id`, `created_at`, `updated_at` (openapi-programs.yaml:9157-9161). `AccountingExportOut` has none (`schemas.py:194-205`) and the model has no `supersedes_export_id` column (`models.py:157-185`).
- [contract] `SyncMapping` and `SyncMappings`. The contract has an `id` per mapping and says rows live in a `sync_mapping` table (openapi-programs.yaml:9126-9135). The code returns no `id` (`schemas.py:141-145`) and stores the list in `external_connection.settings["mappings"]` (`quickbooks.py:248`). The README documents the missing table (line 102-103), so this is a known deviation that the contract does not know about. `external_options` is `{accounts: [...], classes: [...]}` of `{id, name}` (`quickbooks.py:220-226`), which the open contract schema leaves unspecified.
- [undocumented] What `local_key` must be. The contract and ADR 0012 say "tax id", "revenue category id" (openapi-programs.yaml:9131, adr/0012:158-166). The export looks mappings up by posting key: `revenue:<category id>`, `tax_payable:<tax id>`, or the bare ledger account name (`domain/journal.py:18-23`, `service.py:781`). A mapping saved with a raw category id never matches. `put_mappings` also builds `account_map` from `local_key` alone and drops `kind` (`quickbooks.py:246-247`), so two kinds with the same key collide. Neither the README nor the schema says this; `unmapped` lists the posting keys (`quickbooks.py:232`), which is the only hint.
- [missing] ADR 0012 rules with no code. Sub-categories do not inherit a parent's mapping, and sync is not refused until required rows exist (adr/0012:166-169; the contract's `mappings-incomplete` is the same rule). A refresh failure (`invalid_grant`) does not set a `needs_reauth` state, emit `integrations.connection.failed` or notify Owners, and refresh-token rotation is not stored under a row lock (adr/0012:155-158; `quickbooks.py:71-81` lets the exception propagate, `events.py` has only the webhook-disabled event, `ExternalConnection.failure_count` is never written, `models.py:154`). The README does not list these as not built.
- [missing] `getSyncMappings` and every call that needs the access token can refresh and reseal credentials (`quickbooks.py:71-81`, called at :223), so a `GET` writes. The request transaction commits, so the rotated token is kept, but the README's "no mutating GET" rationale for the callback (lines 62-64) does not mention this one.
- [missing] The OAuth round trip cannot complete in a browser. README lines 62-64 say the provider sends the browser to the web page `/integrations/quickbooks/callback`, which POSTs to the API. No such page exists: `web/src` only mentions the callback in the generated `schema.d.ts:4983`, and the default `return_url` `{web_base_url}/setup/integrations` (`quickbooks.py:101`) has no page either. `FakeQuickBooks.authorize_url` redirects to that page too (`adapters/accounting.py:101-102`).
- [missing] A pending QuickBooks connection already carries `connected_at` and `connected_by_staff_user_id`. `create_external_connection` sets both for every provider before `quickbooks.start` flips the status to pending (`service.py:659-661`, `quickbooks.py:100`); the contract says `connected_at` is null until connected (openapi-programs.yaml:9104).
- [undocumented] `receive_webhook` verifies the signature through `connector()`, which returns `FakeQuickBooks` when the three `FH_QUICKBOOKS_*` variables are not all set (`quickbooks.py:41-49, 320`). `FakeQuickBooks.WEBHOOK_SECRET` is a public constant (`adapters/accounting.py:99`), so in any environment without the variables, anyone can sign a body that is accepted and stored, regardless of `integrations.quickbooks_enabled`. An unknown realm is stored as `ignored` (`core/inbound_webhooks.py:56-70`), so such posts also grow the log. The README (lines 69, 104-106) says the simulated adapter is used without the variables but not that the receiver then trusts a public key. Impact on a real tenant was not tested.
- [contract] `receiveQuickBooksEvents` documents `200 No content` and a `429` (openapi-programs.yaml:6964-6980). The code returns `200 {"stored": n}` (`router.py:214-219`, `schemas.py:178-179`) and neither it nor the OAuth callback has a `rate_limit` dependency (only `/public/schedule` does, `router.py:346`).
- [missing] `register_provider_account` is `ON CONFLICT DO NOTHING` (`backend/migrations/versions/0301_billing_module.py:351-356`) and called on connect (`quickbooks.py:152`). Disconnect never removes the lookup row (`service.py:674-688`), so webhooks for a disconnected realm still route to that tenant, and a second tenant connecting the same realm is silently left unrouted. Not tested.
- [undocumented] `run_sync` rules the README leaves out: days in the range that are already `failed` are counted as `failed` and not retried unless `retries_failed` is true (`quickbooks.py:284-285`); today and future days are refused (`last >= today`, :273); a `location_id` in the body is ignored when the connection has its own location (:268). The README says only "at most 31 past days" (line 107).
- [wording] Stale docstrings. `adapters/accounting.py:47-48` says the `QuickBooksOnline` OAuth round trip and refresh-token rotation "are not built"; `QuickBooksConnect` (:130-194) and `quickbooks.py` now build them. `ports/accounting.py:1-5` lists three adapters and does not mention the connect side (`AccountingConnect`, `FakeQuickBooks`, `QuickBooksConnect`, lines 38-72). `router.py:1-3` still says "Every route is require()-gated", but the two inbound QuickBooks routes are not (`router.py:157, 214`).
- [stale-not-built] `docs/status/16-integrations.md:22` says INT-07 is partial and lists "OAuth per location, the class/account mapping table and screen" as not built, and that the export runs only through `POST /accounting-exports`. The OAuth round trip, mappings, settings, sync, retry and webhook now exist (the table and the screen do not).

### Calendar feeds and public schedule

- [contract] `listCalendarFeeds` declares `x-permission: integrations.calendar_feed.revoke_any` (openapi-programs.yaml:7063). The route is a bare `require()` (`router.py:271`): any staff user lists their own feeds, and `revoke_any` only widens the list to others' feeds in their locations (`feeds.py:63-72`). The README (lines 77-79) matches the code, so the contract differs.
- [contract] `updateCalendarFeed` is summarised as "Change filters, or disable and re-enable" (openapi-programs.yaml:7078). `CalendarFeedUpdate` accepts only `name`, `include_shifts` and `status` (`schemas.py:192`).
- [contract] The nine feed and public-schedule operations carry only a summary and permission, with no parameters, request bodies or response schemas: the staff and portal feed operations (openapi-programs.yaml:7057-7099), `getPublicCalendarFeed` (:7100) and the three public-schedule ones (`docs/api/openapi-core.yaml:3354-3380`). The code requires `location_id` on `GET /public/schedule` and `GET /public-schedule-settings`, and takes `from_on` and `days` (1 to 31) on the first (`router.py:331, 349-350`).
- [contract] The three public-schedule operations are tagged `[scheduling]` in the contract, but the generated spec tags them `['integrations', 'scheduling']`, because router-level `tags=["integrations"]` (`router.py:26`) is added to the per-route `tags=["scheduling"]` (:330, 336, 345).
- [contract] `getPublicCalendarFeed` says the token is "revocable and rotatable from the portal" (openapi-programs.yaml:7106-7108). A member can only create a feed: `POST /portal/calendar-feeds` (`router.py:300`) is the only portal route. Disable, re-enable and delete go through `_manage`, which calls `_staff_only` (`feeds.py:137-138`). Repeated POSTs mint unlimited member feeds (`feeds.py:123-134`, no uniqueness check).
- [stale-not-built] Status docs still say calendar feeds and the public schedule are not built: `docs/status/16-integrations.md:23` (INT-08), `docs/status/02-resources-scheduling.md:46-47` (SCH-19, SCH-20), `docs/status/12-staff.md:29` (STF-13), `docs/status/README.md:97-98`. `backend/app/modules/scheduling/README.md:105-106` lists "public schedule (SCH-20)" and "calendar feeds (SCH-19)" under "Not built".
- [undocumented] The README never names `scheduling.public_schedule.manage`, which gates `/public-schedule-settings` (`router.py:331, 338`; registered at `backend/app/modules/scheduling/permissions.py:42`). The settings write audits as `scheduling.public_schedule.update` (`feeds.py:340`). A GET for a location with no row returns unsaved defaults, not a 404 (`feeds.py:316-333`).
- [undocumented] Public schedule delivery details are missing. `GET /public/schedule` is rate limited as `public-schedule`, 60 a minute per IP (`config/app.yaml:77`), and sends `Cache-Control: public, max-age=60` (`router.py:354`); a feed fetch sends `private, max-age=900` (:326). The README states only the feed limit (12 an hour). It also never says `from_on` is clamped to the location's today and `days` to `days_ahead` (`feeds.py:344-353`).
- [undocumented] The README text (lines 80-83) says published sessions come from `scheduling.service.session_window`, but not that this call is capped at `MAX_EVENTS` = 1000 sessions (`feeds.py:30, 359`), and that with `show_sessions` off a published session is dropped from the sessions list and, when `show_busy` is on, appears as a busy time (`feeds.py:368-369`). Line 105 gives the 1000 cap for feeds only.
- [undocumented] `/calendar-feeds*` routes use a bare `require()` (`router.py:271, 279, 288, 296`), so an API key reaches them only to get `403 api-key-not-allowed`. README lines 38-41 name self-service routes and configuration reads as the keyless routes and omit these. `/portal/calendar-feeds` uses `current_ctx` (`router.py:302`) and is outside the key model.
- [undocumented] `DELETE /calendar-feeds/{id}` is a hard delete with an audit record (`feeds.py:170-174`), allowed to the owner or to a `revoke_any` holder for another person's feed. The README says a manager may "never edit or re-enable" others' feeds and says nothing about delete. Cancelled bookings, sessions and games are still emitted as events with a cancelled flag (`feeds.py:223, 263, 282`).
- [wording] README line 78 says a team feed "needs a league game key". The code accepts either `leagues.game.manage` or `leagues.result.enter` (`feeds.py:33`, `GAME_READS`), rechecked on each fetch, so a feed goes empty when the owner loses both (`feeds.py:246`).
- [undocumented] `feeds.py` reaches into other contexts' submodules, not only top-level packages: `platform.staff.principal_for` (:301), `programs.selfservice.portal_list_enrollments` (:272), `scheduling.service.*`, `staff.service.list_my_shifts` (:227), and `platform.service.client_identity_is_active` (`backend/app/modules/platform/service.py:551`, called at `feeds.py:297`). CLAUDE.md's boundary rule says top-level package only. Whether `make boundaries` allows it was not run.
- [missing] CLAUDE.md requires every new table to be populated by `populate()` so the generated isolation tests cover it. `calendar_feed` is enrolled (`backend/conftest.py:1243`, `backend/tests/test_isolation.py:483`). `public_schedule_setting` has a row created through a PATCH (`backend/conftest.py:1237-1240`), but its id is not in the `populate()` return value. Whether another test covers its isolation is unverified.
