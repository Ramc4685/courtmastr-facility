## backend/app/modules/engagement/README.md

- [contract] Line 112 names the mobile adapter as `mobile/src/api/api.ts`. That file does not exist. The adapter is `mobile/src/adapters/api.ts`, and `mobile/src/api/` holds only `client.ts`, `errors.ts`, `schema.d.ts` and `types.ts`.
- [wording] Line 104's heading, "Endpoints the mobile app depends on (keep stable)", overstates what the app uses. The adapter calls only `GET /portal/inbox` (without `client_id`), `POST /portal/inbox/{id}/read` and `POST /portal/devices` (`mobile/src/adapters/api.ts:178-182`). Nothing in `mobile/src` outside the generated `schema.d.ts` calls `/portal/inbox/unread-count`, `DELETE /portal/devices/{id}`, `/portal/videos`, `/public/portal-config` or `/portal/clients/{client_id}/communication-preferences`.
- [wording] Lines 112-114 list the other portal routes the adapter maps, and the list is incomplete. It also calls `/portal/session-listings` (`mobile/src/adapters/api.ts:37`), `/portal/enrollments` and `/portal/enrollments/{id}/cancel` (`api.ts:90,126,133`), `/portal/app-cards` (`api.ts:118`) and `/portal/assessment-bests` (`api.ts:177`).
- [undocumented] Line 109 lists only `GET /portal/videos`. The router also serves `GET /portal/videos/{video_id}` (`router.py:439`, calling `service.get_portal_video` at `service.py:1819`). This route is an uncommitted addition in the worktree.
- [contract] The README says the context's endpoints are the contract (lines 104-110), but `docs/api/openapi-programs.yaml` tags many operations `engagement` that no route serves, and Not built (lines 116-120) lists none of them. Evidence is the router (`router.py:37-479`) against the spec. Operations missing from the code:
  - `POST /webhooks/email/{provider}`. README deviation 6 (lines 80-82) says the webhook is not built, but this is not in Not built.
  - Campaign operations: `POST /campaigns/{id}/resume`, `/unschedule`, `/copy` and `/audience-preview`.
  - Media library: `GET|POST /media-assets` and `DELETE /media-assets/{id}`.
  - App content: `/news-stories` (and `/public/news-stories`), `/home-screens`, `/app-tiles`, `/portal-content*`, `/portal/content`, `/locations/{id}/app-content`, `/app-config`, `/public/app-config` and `/public/app-directory`.
  - Portal and public intake: `/portal-invitations*`, `/public/portal-invitations/*`, `/trial-requests*`, `/portal/favorites*`, `/portal/app-events`, `/portal/menu` and `/app-analytics`.
  - The email-verification routes in this spec file are served by `clients/router.py`, not engagement.
- [contract] The spec and the code disagree on the shape of some routes:
  - The spec has `POST /campaigns/{id}/test-send` (`openapi-programs.yaml:4633`); the code has `POST /campaigns/{id}/test` (`router.py:202`).
  - The spec has `GET|PUT /portal/communication-preferences` (`openapi-programs.yaml:~4196`); the code has `/portal/clients/{client_id}/communication-preferences` (`router.py:51,56`).
  - The spec has `POST /public/unsubscribe/{token}`; the code takes the token in the body at `POST /public/unsubscribe` (`router.py:457`), which matches README lines 27-29.
  - The spec names the device path parameter `device_id`; the code uses `device_registration_id` (`router.py:427`).
- [undocumented] The context emits three events that the README never mentions: `engagement.campaign.sent` (`events.py:9-14`; `service.py:978`), `engagement.message.bounced` (`events.py:17-21`; `service.py:1164`) and `engagement.consent.changed` (`events.py:24-28`; `service.py:1183,1224`).
- [undocumented] Portal inbox items expire 30 days after publication. `INBOX_DAYS = 30` (`service.py:351`) sets `expires_at` on announcement and automation items (`service.py:949,1459`), and expired items are hidden (`router.py:406`; `service.py:1248-1249`). Deviation 4 (lines 73-78) covers read state and recall but not expiry.
- [undocumented] Two permission keys are registered but no code uses them: `engagement.sms_campaign.send` and `engagement.inbox.reply` (`permissions.py:19,23`). SMS is listed as not built (line 119). Replying to client messages is not, and no route offers it.
- [undocumented] Line 14 says `subject.py` holds the merge and data-subject handlers, but it covers only the four messaging tables (`subject.py:13,46-47`). A second pair of handlers, for `communication_preference` and `consent_event`, lives in `service.py`, registered as `"engagement"` (`service.py:286-340`).
- [undocumented] Built-in segments are read-only. An edit or delete gets `409 segment-read-only` (`service.py:687,704`), and the segments are seeded by `BUILTIN_SEGMENTS` / `ensure_builtin_segments` (`service.py:732-748`). The README also omits the system-template catalogue `SYSTEM_TEMPLATES` / `system_template` (`service.py:581-602`) and `POST /segments/preview` (`router.py:111`). Line 51-53 says "system template" without saying where those come from.
- [undocumented] Releasing a suppression has two refusals the README does not mention: `409 suppression-permanent` for an address that failed again after a release, and `409 invalid-state-transition` for a second release (`service.py:1124,1126`). Line 56 says only "permanently after a release".
