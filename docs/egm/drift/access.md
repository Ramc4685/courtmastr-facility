- `GET /clients/{id}/access-mode` (router.py:176-179, key `access.checkin.create`) is not in the README. README 59-60 covers only `PUT`.
- The event `access.check_in.session_booked` (events.py:30, published at kiosk.py:129 and desk.py:224) is not listed. README 49 and 147 name `granted`, `denied` and `checked_out`.
- The module consumes `clients.client.disabled` and revokes the client's wallet passes (handlers.py:7-12, `service.revoke_wallet_passes_of`, service.py:599). The wallet-pass section and the merge and erasure bullet (README 157-161) do not mention it.
- Issuing a wallet pass, an app card or a generated credential requires an active client (`clients.service.require_active`, service.py:440, 510, 558). The README does not say so.
- Kiosk name search needs `lookup_method` to allow it, a prefix of at least 3 letters (schemas.py:425-427), lists at most 5 (`NAME_MATCHES`, service.py:65, 843) and never lists disabled clients' value lookups (`client.status == "active"`, service.py:834). Lookup refusals are 422 `lookup-method-disabled` (service.py:833, 837, 869). README 73-76 says only that minors are not listed.
- `lookup_method = name` also refuses a scanned member-number barcode at check-in (`card_payload` with no credential row: 422 `lookup-method-disabled`, service.py:868-869) and a typed member number at lookup (service.py:826-833). The README does not say. Because `resolve` runs first, such a refused value was known, so it is not counted toward the lock.
- A value the kiosk cannot match is 422 `card-invalid` (service.py:862-867); the README gives no error code for it. A staff user scanning at the window is not covered by the lockout (`resolve` is called directly), which the README does say (staff are signed in).
- Lockout details the README does not give: the 60-second grace on the Redis TTLs (service.py:775, 778), and the `unknown_value_count` helper for tests and support (service.py:760-764). The README now covers what counts (unknown, expired or revoked card or pass), the `kiosk-locked:<device>` key, the 429 on lookups and check-ins alike, the sliding window, the fail-open behaviour and that a known value does not reset the count.
- The kiosk cookie lives 400 days (`max_age=400 * 86400`, router.py:402). The README gives no lifetime.
- `kiosk.visit()` spends the visit token with one `DELETE ... RETURNING` (kiosk.py:51-68). README 98-100 states this and `test_a_visit_token_cannot_be_spent_twice_concurrently` (tests/test_kiosk_reservations.py:267) covers it, but the README cites no test. The possession and lockout rules also have tests the README does not cite: `test_a_static_card_value_is_never_possession` (:289), `test_unknown_values_lock_the_kiosk_even_between_known_ones` (:310) and `test_concurrent_unknown_values_are_all_counted` (:336). The tests drive Redis, so they need it in the test environment; neither the README nor the access test notes say so.
- The household lockout. `clients.households.household_ids` (households.py:353-365) is symmetric: the visitor's lockout comes from a past-due invoice billed to the visitor or to any client one live relationship away whose type grants acting rights in either direction. README 88-90 names only the child billed to a parent; a parent is equally locked through a child's past-due invoice. The only test, `test_a_child_billed_to_a_past_due_parent_cannot_book_at_the_kiosk` (`backend/app/modules/billing/tests/test_collections.py:76`), lives in billing and covers the child case only. Nothing in `access/tests/` covers the household lockout.
- The README's reverted-purchase bullet gives rules for a future version (a fresh app-QR step, no bare wallet passes, one purchase per check-in, a daily cap) but no code, test or contract places mark them. Nothing in the code prevents a later purchase route from skipping them.
- Wallet pass as possession: README 108 and service.py:62-64 call an active wallet-pass token a secret that proves possession, while the reverted-purchase bullet calls a wallet pass "a static bearer barcode". Both are in the README, and the code treats a wallet pass as possession for booking a credit-paid session (kiosk.py:31, 142). Which statement is the rule is unsettled.

The README uses both vocabularies without saying which is which. README 13 is right for the stored value.

- README 105-106 says "Spending anything at the kiosk (a package credit, and in future a membership visit, an account charge or a payment) needs identification by possession". The only spend built is a package credit through `programs.selfservice.kiosk_enroll`; "in future" is accurate but the bullet reads wider than the code.
- README 108-111 says the tablet sends scanner bursts as `card_payload`. `web/src/features/access/KioskPage.tsx:136` does so and sends a picked name match as `match_token` (:209), so the kiosk page agrees, and its comment now says the server decides possession from the value. The README does not link that file. The kiosk lookup route accepts `credential_value` from any device-token client, and the rule rests on the server alone (service.py:871).
