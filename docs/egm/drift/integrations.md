### API keys and the contract's security model

- [contract] The contract marks 28 integrations operations as callable with an API key (`security: [{staffSession: []}, {apiKey: []}]`): `createApiKey` (openapi-programs.yaml:6396), `rotateApiKey` (6418), `revokeApiKey` (6436), the webhook, delivery, connection, mapping, export, sync and adapter operations. Code can never grant a key the scopes they need: `KEY_CONTEXTS` excludes `integrations` (`service.py:68-72`) and every route is gated by an `integrations.*` key (`permissions.py:14-19`). README lines 34-38 and `docs/api/public-api-guide.md:29-32` say keys cannot create, rotate or revoke keys. In practice all 28 answer `403 api-key-not-allowed` to a key.
- [wording] README lines 36-37 name the contexts off the allow-list as "platform, reporting, integrations, staff and engagement". `KEY_CONTEXTS` (`service.py:68-72`: access, assessments, billing, clients, documents, leagues, memberships, packages, pos, programs, rentals, resources, scheduling) also leaves out `imports`, which has its own module directory.
- [undocumented] `auth.authenticate` (`auth.py:93`) also refuses a key when the tenant is not active (`403 tenant-suspended`, `auth.py:95-96`) and when the plan lacks `api_access` (`auth.py:97`; the same gate is on create and rotate, `service.py:144, 178`), and writes `last_used_at` at most once a minute (`auth.py:103-104`). README line 10 (the `auth.py` row) and lines 34-46 mention none of these.
- [undocumented] `models.py:60-61` (`ApiKey` docstring) still says grants are "scopes intersected with the creator's current grants"; `auth._bounded` also drops any scope off the allow-list, as README lines 40-42 say. Migration 1705 (`migrations/versions/1705_integrations_key_scope_allow_list.py`) freezes a second copy of the contexts; nothing ties it to `KEY_CONTEXTS`.

### INT-07 QuickBooks Online

- [contract] Deliberate deviation, written down (README lines 72-75). `completeExternalConnectionOAuth` is an anonymous `GET` with query params answering `302` (openapi-programs.yaml:6756); the code is `POST /external-connections/oauth/callback`, a staff route with a JSON body answering `200 {external_connection_id, status, return_url}` (`router.py:159-168`, `schemas.py:176-189`). The contract also types `realm_id` as a uuid; the code takes digits only (`schemas.py:179-181`).
- [contract] Path parameter is `connection_id` in the contract for every `/external-connections/{connection_id}...` operation and `external_connection_id` in the code (`router.py:170-237`).
- [contract] `ExternalConnection` (openapi-programs.yaml:9260) returns `granted_scopes`, `settings`, `updated_at` and `authorize_url` while pending. `ExternalConnectionOut` has none of the first three (`schemas.py:128-140`) and `authorize_url` exists only on the create response (`schemas.py:141-143`). A pending link cannot be fetched again and patched settings cannot be read back; `return_url`, mappings and the `sync` job state live in that `settings` blob.
- [contract] `createExternalConnection` documents `409 connection-exists` and `422 provider-not-available` (openapi-programs.yaml:6733, 6753). The code's `provider` is a three-value `Literal` (`accounting_file`, `quickbooks_online`, `zoom`; `schemas.py:118`); other values are a generic validation 422, and `accounting_file` and `zoom` are not in the contract enum. QuickBooks with the flag off is `422 provider-not-configured` (`service.py:662-665`); a duplicate (provider, location) is the generic `409 already-exists` via `uq_external_connection`, not `connection-exists`. The body also takes `zoom` and `settings` (`schemas.py:117-126`), which `ExternalConnectionCreate` lacks (openapi-programs.yaml:9284).
- [contract] `updateExternalConnection` says settings are "sync_from date, sync mode (invoice or daily summary), auto-sync flag" (openapi-programs.yaml:6802). The code accepts `default_income_account`, `sync_from`, `auto_sync` (`quickbooks.py:37`); there is no sync mode, and `sync_from` is an unvalidated string.
- [contract] `runSync` (openapi-programs.yaml:6928) answers an `Accepted` handle `{job_id, status: queued|running|succeeded|failed, resource_url}`. The code queues (202, `router.py:202`, `quickbooks.py:303-343`) but `SyncRunOut` is `{status, counts, status_url}` (`schemas.py:195-199`), status `running|completed|failed`, no `job_id`. It syncs one location per call (`location_id` body field the contract's `SyncRun` lacks, `schemas.py:169-174`; openapi-programs.yaml:9341). `mappings-incomplete` (declared at 6949) is never raised: an unmapped key fails that day with a plain validation message (`service.py:827-832`).
- [contract] `getSyncStatus` (openapi-programs.yaml:6951) and `resetSync` (6969) answer `200` with no schema, and `SyncStatusOut` (`schemas.py:201-210`) is not in the contract. `getSyncMappings` still declares `x-problem-codes: [provider-unavailable]` (6864) though the code now answers `200` with `options_unavailable` (`quickbooks.py:270-274`, `schemas.py:162-167`), a field the contract's `SyncMappings` (9308) lacks.
- [contract] `listAccountingExports` is not served at its contract path (`/external-connections/{connection_id}/accounting-exports`, openapi-programs.yaml:6891). The flat `GET /accounting-exports` (`router.py:244`) lacks `business_on[gte|lte]` and `status[in]` (`service.py:848-861`). `POST /accounting-exports` (`router.py:250`), `GET /api-reference` (264) and `/integration-adapters` (258) exist in the router; confirm each has a contract entry.
- [contract] `AccountingExport` (openapi-programs.yaml:9322) has `supersedes_export_id`, `created_at`, `updated_at`; `AccountingExportOut` has none (`schemas.py:218-230`) and `models.py:157-182` has no `supersedes_export_id` column.
- [contract] `SyncMapping` and `SyncMappings` (openapi-programs.yaml:9298, 9308) have an `id` and a `sync_mapping` table. The code returns no id and keeps the list in `external_connection.settings["mappings"]` (`quickbooks.py:277-300`, `schemas.py:151-168`). README lines 155-156 admit the missing table; the contract does not.
- [contract] `receiveQuickBooksEvents` (openapi-programs.yaml:7106) documents `200` no content and a `429`. The code returns `200 {"stored": n}` (`router.py:229-235`, `schemas.py:191-193`) and has no `rate_limit` dependency on that route.
- [contract] The Intuit request id: the contract says it derives from the export id and ADR 0012 says `"{tenant_id}:qbo_je:{accounting_export.id}"` (docs/adr/0012-integrations-and-public-api.md:181). The code uses `uuid5` of connection, location and day (`service.py:844`), as README lines 66-68 say; contract and ADR were not updated.
- [contract] ADR 0012 (docs/adr/0012-integrations-and-public-api.md:183-190) expects "Sync now" to export earlier unexported days too, and a successful export to advance `tenant.billing_locked_through_on`. The code exports exactly the requested range (`quickbooks.py:324-327`) and nothing in the module touches `billing_locked_through_on`. README lines 155-156 and 179-180 do not list either as not built.
- [undocumented] What `local_key` must be. The contract and ADR say "tax id", "revenue category id" (openapi-programs.yaml:9298; ADR 0012:158-166); the export matches by posting key `revenue:<category id>`, `tax_payable:<tax id>` or the ledger account name (`domain/journal.py:18-23`, `service.py:827`). A raw id never matches. README line 89 says only that posting keys are unique across kinds.
- [undocumented] ADR 0012 refresh failure rules are not in the README's not-built list (it names `needs_reauth`, line 180): a refresh failure emits no `integrations.connection.failed` and notifies no Owner (`quickbooks.py:100-108`; `events.py` has only the webhook-disabled event), and `ExternalConnection.failure_count` is never written for connections (`models.py:155`).
- [undocumented] `credentials()` locks the connection row and reloads the ciphertext on every call, not only when a refresh is due (`quickbooks.py:83-98`), so `get_mappings`, `revoke` (:198) and each posting hold the lock. README lines 162-164 say only "due tokens are refreshed under a row lock". `refresh_if_due` catches every `Exception` (:106), including a database error that would poison the transaction. `GET .../sync-mappings` can refresh and reseal credentials, so a GET writes; README lines 72-74 justify the POST callback by "no mutating GET" without saying so.
- [undocumented] `run_sync` rules the README (lines 160-166) leaves out: a sync needs an `active` connection (`409`, `quickbooks.py:312-313`); a body `location_id` is ignored when the connection has its own (:319); today and later are `422` at queue time (:325); days already `failed` count as `failed` and are not retried unless `retries_failed` (:416); a connection disconnected mid-job ends the job `failed` with no count for the remaining days.
- [undocumented] Stale-sync takeover has gaps the README (lines 164-167) leaves out. A sync is identified only by `settings.sync`, with no job id or generation, so a takeover (`quickbooks.py:314-316`, `_live` :359) enqueues a second chain while a slow first chain may still run; both advance one cursor under the row lock (`sync_chunk`, :391-430) and the old chain's dead-letter hook `fail_sync` (:431-437, `jobs.py:34-36`) marks whichever job is `running` as failed, including the new one. A job stored before `beat_at` existed is stale at once (:354-356). The takeover is audited only as `integrations.sync.start` (:331). `integrations.sync.reset` (:376) and `GET .../sync` being gated by `integrations.sync.run` (`router.py:210`) are not in the README.
- [undocumented] The pending or errored connection takeover (README lines 176-178) is wider than the text. `create_external_connection` matches on provider and location only, for every provider, and rewrites `settings` (mappings, `account_map`, any `sync` cursor), credentials, `external_account_*`, `connected_by_staff_user_id` and `last_error` (`service.py:654-698`); the audit record is still `integrations.connection.create`. A takeover also kills an earlier starter's link (`quickbooks.py:167-168`, `403 state-invalid`). Only QuickBooks writes `pending` and `error`, so other providers never hit this branch.
- [undocumented] The export doc number is `FH-<SLUG>-<YYYYMMDD>` in README line 66, but the slug is upper-cased and cut to 12 characters (`service.py:793`), so two locations sharing a 12-character slug prefix share a doc number on a day.
