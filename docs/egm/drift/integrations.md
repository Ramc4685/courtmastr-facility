### INT-07 QuickBooks Online

- [contract] Deliberate deviation, written down in the README (lines 64-67). `completeExternalConnectionOAuth` is an anonymous `GET` (`security: []`, `x-permission: oauth-state`) with `state`, `code`, `realm_id`, `error` in the query and answers `302` (openapi-programs.yaml:6745-6770). The code serves `POST /external-connections/oauth/callback`, a staff route gated by `integrations.connection.manage` that also needs a signed-in person, with a JSON body, and answers `200 {external_connection_id, status, return_url}` (`router.py:159-167`, `schemas.py:176-188`). The yaml still describes the old shape. It also types `realm_id` as `format: uuid`, but the code takes digits only (`schemas.py:179`).
- [contract] Path parameter is `connection_id` in the contract for every `/external-connections/{connection_id}...` operation (openapi-programs.yaml:6771, 6811, 6834, 6875, 6912) and `external_connection_id` in the code (`router.py:170-227`). Same URL, different name in the generated spec and in `web/src/api/schema.d.ts`.
- [contract] `ExternalConnection` response. The contract returns `granted_scopes`, `settings`, `updated_at` and `authorize_url` "while pending" (openapi-programs.yaml:9085-9107). `ExternalConnectionOut` has none of the first three (`schemas.py:129-139`) and `authorize_url` exists only on the create response (`schemas.py:142-143`, `router.py:156`). A pending link cannot be fetched again and patched settings cannot be read back; `return_url`, `mappings`, `account_map` and `class_map` live in that same `settings` blob (`quickbooks.py:112, 278`).
- [contract] `createExternalConnection`. The contract documents `409 connection-exists` and `422 provider-not-available` (openapi-programs.yaml:6742-6744). Code: `provider` is a three-value `Literal` of `accounting_file`, `quickbooks_online`, `zoom`, `google_analytics` (`schemas.py:118`; four since INT-13), so any other provider (the contract's enum also lists smartwaiver, perkville and more, openapi-programs.yaml:9094) is a generic validation 422 and `accounting_file` and `google_analytics` are in the code but not the contract enum; QuickBooks with the flag off is `422 provider-not-configured` (`service.py:653-656`), not listed; a duplicate (provider, location) hits `uq_external_connection` (`models.py:138-140`) and returns the generic `409 already-exists`. The body also accepts `zoom` (the tenant's Server-to-Server app) and `settings` (`schemas.py:119-125`), which the contract schema lacks (openapi-programs.yaml:9109-9116).
- [contract] `updateExternalConnection` says settings are "sync_from date, sync mode (invoice or daily summary), auto-sync flag" and the body is `application/merge-patch+json` (openapi-programs.yaml:6803, 9120-9124). The code accepts `default_income_account`, `sync_from`, `auto_sync` (`quickbooks.py:37`); there is no sync mode, and `sync_from` is an unvalidated string (`schemas.py:146-149`; the description lists only the QuickBooks keys, not the analytics ones).
- [contract] `runSync` is a job that "creates or retries the accounting_export row of each location and day in the range" and answers an `Accepted` handle (openapi-programs.yaml:6919-6940). The code runs in the request (README line 146 says so) for one location (`quickbooks.py:298`), returns `{status: "completed", counts, status_url}` (`schemas.py:195-198`), takes `location_id` which the contract's `SyncRun` lacks, and has no `local_kinds` (`schemas.py:169-174`; contract openapi-programs.yaml:9170-9176). `mappings-incomplete` (422) is never raised: an unmapped QuickBooks key fails that day with a plain validation message (`service.py:814-815`), a revenue key with a default income account posts with a warning (:811-813).
- [contract] `listAccountingExports` is not served at its contract path (openapi-programs.yaml:6875). The flat route that is served lacks the `business_on[gte]`, `business_on[lte]` filters and the `status[in]` form (`router.py:230-233`, filter fields in `service.py:833-841`).
- [contract] `AccountingExport` response. The contract has `supersedes_export_id`, `created_at`, `updated_at` (openapi-programs.yaml:9157-9161). `AccountingExportOut` has none (`schemas.py:207-218`) and the model has no `supersedes_export_id` column (`models.py:158-186`).
- [contract] `SyncMapping` and `SyncMappings`. The contract has an `id` per mapping and a `sync_mapping` table (openapi-programs.yaml:9126-9135). The code returns no `id` (`schemas.py:152-168`) and keeps the list in `external_connection.settings["mappings"]` (`quickbooks.py:278`). The README admits the missing table (lines 141-142); the contract does not know. `external_options` is `{accounts, classes}` of `{id, name}` (`quickbooks.py:248-254`), which the contract leaves unspecified.
- [contract] `receiveQuickBooksEvents` documents `200 No content` and a `429` (openapi-programs.yaml:6964-6980). The code returns `200 {"stored": n}` (`router.py:215-220`, `schemas.py:191-192`) and neither it nor the OAuth callback has a `rate_limit` dependency (only the two public GETs do, `router.py:377`, `392`).
- [undocumented] What `local_key` must be. The contract and ADR 0012 say "tax id", "revenue category id" (openapi-programs.yaml:9131, adr/0012:158-166). The export looks mappings up by posting key: `revenue:<category id>`, `tax_payable:<tax id>`, or the bare ledger account name (`domain/journal.py:18-23`, `service.py:810`). A mapping saved with a raw category id never matches. README lines 81-82 mention that posting keys are unique across kinds but not that `local_key` must be one; `unmapped` lists the posting keys (`quickbooks.py:260`), the only hint.
- [undocumented] ADR 0012 refresh rules the README does not list as not built (its lines 156-157 name only `needs_reauth`). A refresh failure (`invalid_grant`) emits no `integrations.connection.failed` and notifies no Owner, rotation is not stored under a row lock (adr/0012:155-158; `quickbooks.py:90-92` lets the exception propagate, `events.py` has only the webhook-disabled event), and `ExternalConnection.failure_count` is never written (`models.py:155`).
- [undocumented] `getSyncMappings` and every call that needs the access token can refresh and reseal credentials (`quickbooks.py:82-92`, called at :251), so a `GET` writes. The README rationale for a POST callback ("no mutating GET", lines 66-67) does not mention it. The request transaction commits, so the rotated token is kept.
- [undocumented] `run_sync` rules the README leaves out (its line 146 gives only the 31-day cap): days already `failed` are counted as `failed` and not retried unless `retries_failed` is true (`quickbooks.py:314-315`); today and future days are refused (`last >= today`, :303); a body `location_id` is ignored when the connection has its own (:298).
- [stale-not-built] `docs/status/16-integrations.md:22` says INT-07 lists "OAuth per location, the class/account mapping table and screen" as not built and the export runs only through `POST /accounting-exports`. The OAuth round trip, mappings, settings, sync, retry and webhook now exist (the table and screen do not). Line 28 says INT-13 is not built ("Needs the public portal pages"); see the INT-13 section below. Line 24 says INT-09 has only the simulated adapter and lists "Zoom OAuth ... the entitlement-checked join redirect, and attendance" as not built; a Zoom connection, the session meeting routes, the join and the attendance mark now exist (see below).

### Calendar feeds and public schedule

- [contract] `listCalendarFeeds` declares `x-permission: integrations.calendar_feed.revoke_any` (openapi-programs.yaml:7063). The route is a bare `require()` (`router.py:271`): any staff user lists their own feeds, and `revoke_any` only widens the list to others' feeds in their locations (`feeds.py:63-72`). The README (lines 90-92) matches the code, so the contract differs.
- [contract] `updateCalendarFeed` is summarised as "Change filters, or disable and re-enable" (openapi-programs.yaml:7078). `CalendarFeedUpdate` accepts only `name`, `include_shifts` and `status` (`schemas.py:301`).
- [contract] The nine feed and public-schedule operations carry only a summary and permission, with no parameters, request bodies or response schemas: the staff and portal feed operations (openapi-programs.yaml:7057-7099), `getPublicCalendarFeed` (:7100) and the three public-schedule ones (`docs/api/openapi-core.yaml:3354-3380`). - [contract] The three public-schedule operations are tagged `[scheduling]` in the contract, but the generated spec tags them `['integrations', 'scheduling']`, because router-level `tags=["integrations"]` (`router.py:28`) is added to the per-route `tags=["scheduling"]` (:361, 367, 376).
